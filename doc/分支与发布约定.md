# 分支与发布约定

> 2026-11-19 修订：`main` = 稳定基线（无调试代码）；`develop` = `main` + **仅叠在 tip 上的调试层**（可重建）；短生命周期分支命名须带 **`YYYY-MM-DD` 日期戳**。  
> 仍用开关裁剪「无会员 / 有会员 / 广告」，不维护多条「产品形态」长期分叉。

## 分支角色

| 分支 | 角色 |
|------|------|
| **`main`** | **稳定 / 可上线**基线；**不含调试代码**；**新功能与修复都从这里拉分支** |
| **`develop`** | **联调床** = 当前 `main` + 调试叠加（会员页调试区、`dev*` 等）；可含未通过试验；**可随时按下面步骤重建** |
| **`feat/*` · `fix/*`** | **必须从 `main` 拉出**；通过后合回 **`main`**；需要带调试验证时可合进 **`develop`** |

**禁止：** 为「无会员 / 有会员」再开两条长期产品分支；无会员用 `MEMBERSHIP_ENABLED=false` 即可。

## 正确流向

```
main（稳定、无调试）
  ├──► feat/<topic>-YYYY-MM-DD ──► 通过后合回 main
  │                              └──►（可选）合进 develop 做带调试联调
  └── merge / rebase ──► develop = main +「仅 develop 的调试提交」
```

- **不要**从 `develop` 拉新功能：`develop` 可能含未通过代码。  
- **不要**把整支脏的 `develop` 合进 `main`。  
- **可以**把 `main`（或基于 `main` 的 `feat`）合进 `develop`：调试是 develop **额外加上去的**，不是 main 上「删掉」的历史，合并不会冲掉调试层（若冲突，保留 develop 侧调试改动即可）。

## 分支命名

短生命周期功能 / 修复分支 **必须带日期戳**，避免同名长期漂浮、worktree 与远程混淆。

| 类型 | 格式 | 示例 |
|------|------|------|
| 功能 | `feat/<topic>-YYYY-MM-DD` | `feat/membership-2026-11-19` |
| 修复 | `fix/<topic>-YYYY-MM-DD` | `fix/pay-timeout-2026-11-20` |
| 发版/热修（可选） | `release/<tag或日期>` | `release/2026-11-19` |

- `<topic>`：小写英文短横线，一事一题；不要用笼统的 `feat/wip`、`feat/tmp`。  
- 日期用拉分支当天的 **本地日历日**（`YYYY-MM-DD`）。同一 topic 当天需再开第二条时，在日期后加时间：`feat/<topic>-YYYY-MM-DD-HHmm`。  
- **不要**使用无日期的永久名（如 `feat/membership`）；合入 `main` 后可删本地/远程该分支。  
- 长期只保留 **`main`** 与 **`develop`**；其余均为短生命周期。

## `develop` 调试层（清单与重建）

调试 **只存在于 `develop` tip 之上**，不进 `main`。内容包括：

- 会员页「调试（仅开发/体验版）」整块 UI 与 `onDev*`  
- `miniprogram/services/membership.js` 中 `devGrant` / `devClear` / `devExpireSoon` / `devResetFirstPurchase` / `devClearOrders` / `devCreatePending`  
- 云函数 `membership` 的对应 `dev*` action；联调云可设 `MEMBERSHIP_ALLOW_DEV_GRANT=1`（正式云禁止）  
- 首页「清除「更多餐」广告解锁（测试）」与 `clearDailyMealCustomUnlock`（产品侧 `unlockDailyMealCustom` 在 `main`/`feat`；**清除**仅 `develop`）  
- 仅服务于调试按钮的单测 / 联调 README 说明  

**`main` 保留：** `MEMBERSHIP_ENABLED`、`ADS_ENABLED`、正式支付与换菜/菜数软限、正式埋点。

### 重建 `develop`（联调床脏了或丢调试时）

```bash
git checkout main
git branch -f develop main
git checkout develop
# 从仍含调试的历史 tip 取回调试相关文件后提交，例如：
git checkout 6533753 -- \
  cloudfunctions/membership/index.js \
  cloudfunctions/membership/index.test.js \
  cloudfunctions/membership/README.md \
  miniprogram/pages/membership/index.js \
  miniprogram/pages/membership/index.test.js \
  miniprogram/pages/membership/index.wxml \
  miniprogram/pages/membership/index.wxss \
  miniprogram/services/membership.js
# 再把本分支 README 的「调试开关」说明写回后：
git commit -m "chore: restore membership debug overlay on develop"
```

也可对 strip 提交做 `git revert --no-edit 7536e5d`（若与后续文档改动冲突则手动解决，保留 develop 侧调试代码）。

日常跟上 `main`（推荐让调试提交始终在 tip）：

```bash
git checkout develop
git rebase main    # 或: git merge main
```

若试验合入太多、`develop` 太乱：直接按上面 **重建**，不必珍惜脏历史。

## 功能开关（`main` / `develop` 都有实现，发版改常量）

| 开关 | 位置 | 说明 |
|------|------|------|
| `MEMBERSHIP_ENABLED` | `miniprogram/services/membership.js` | 默认建议 `false`（无会员先上）；卖会员改 `true` |
| `ADS_ENABLED` | `miniprogram/utils/ads.js` | 默认 `false`；流量主就绪后再开 |

## 合入 `main` 的规则

- 只合 **已通过** 的 `feat` / `fix`（或等价 cherry-pick），**不要**整支 merge `develop`。  
- 合入内容 **不得**含调试 UI / `dev*`。若某 PR 误带调试：合入前删掉，或只用 `main` 上的干净提交。  
- `main` 上 **不要**再做「为了同步而 merge develop」。

## 发版前核对

- [ ] 发布检出的是 **`main`**  
- [ ] `main` 无会员调试区、无 `dev*` 客户端/云入口  
- [ ] `MEMBERSHIP_ENABLED` / `ADS_ENABLED` 符合本轮  
- [ ] 正式云无 `MEMBERSHIP_ALLOW_DEV_GRANT=1`
