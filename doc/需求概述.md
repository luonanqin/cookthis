## 产品需求文档：买菜做什么 / cookthis（微信小程序）

### 产品名称

| 语言 | 名称 | 用途 |
|------|------|------|
| 中文 | **买菜做什么** | 微信小程序展示名、用户可见文案 |
| 英文 | **cookthis** | 工程名、仓库名、技术标识 |

> 一句话：站在菜场里，打开「买菜做什么」，告诉它今天有什么，它告诉你回去做什么。

**中文名说明（2026-10-08）**：
- 「做什么菜」等原先名称**已被占用**；曾暂定「做道菜」。
- **正式展示名：买菜做什么**（场景贴合：买菜现场 → 决定做什么）。
- 英文工程名 **cookthis** 不变。
- 流量侧仍可在搜索关键词 / 简介中覆盖 `吃什么菜`、`今天吃什么`、`做什么菜` 等热词（获客词与展示名分流）。
- 小程序后台展示名需与本表同步。

### 市场突破点

相对下厨房、美团买菜菜谱、各类「今日吃什么」工具，本产品的切入点不是「先想好吃什么再找做法」，而是**站在菜场决策现场**：用「今天有什么」倒推出「买哪几样 + 回去做什么」。

1. **场景卡位：菜场即时决策**  
   用户痛点发生在摊位前（时间紧、选择多、怕买多买重）。小程序服务「确认在售食材 → 出方案 → 出购买清单」闭环，比回家后再翻菜谱更贴决策瞬间。

2. **供需反转：有什么 → 做什么**  
   默认确认时令菜（全选、有上限）；四季常见主料默认计入但不占主列表；再结合人数、搭配、几顿饭出推荐。

3. **家庭真实约束，而不只是个人口味**  
   家庭忌口硬排除、成员忌口占比软约束、菜式品类偏好、避开近期已吃过——解决「一人决定全家吃腻 / 踩雷忌口」的家常难题，聚会与日常场景分流。

4. **一次买多顿，清单可执行**  
   支持「想做几顿」规划，在某一方案旁点「去买菜」直达购买食材页（按分类、每行两个勾选），把推荐落到菜场可勾选的采购动作，而不是停在菜名列表。

5. **微信搜一搜与场景关键词**  
   展示名「买菜做什么」；简介与搜索词可覆盖「做什么菜」「吃什么菜」「今天吃什么」等问句，利于搜一搜匹配与内容种草；配合进场确认饮食记录，形成「用一次 → 记一次 → 下次更准」的留存钩子。

**命名决策**：
- 「做什么菜」小程序名**已被占用**；不改为纯「吃什么菜」作主名（偏外卖/下馆子，流量杂）。
- **正式展示名：买菜做什么**（2026-10-08 确认）。
- **流量侧借用热词**：小程序搜索关键词、简介优先覆盖 `吃什么菜`、`今天吃什么`、`做什么菜` 等，与展示名分流。
- 英文工程名 **cookthis** 不变。

### 商业模式（摘要）

> 全文见 [`doc/盈利模式方案.md`](./盈利模式方案.md)。

- **最终路径**：**先广告、后会员**。流量主达标后，在购买食材页（用户**于摊位挑真菜、对照清单**时）放原生广告（日常 1 条；**聚会**清单更长可 2 条，不插屏），用收入支撑能力建设；有稳定使用数据后再上会员（去广告 + 换一批/多顿/成员等；**不以锁聚会作付费墙**）。  
- **主链路免费**：**日常与聚会**推荐与清单均可走完，不设付费墙。  
- **候选保留**：电商分佣、品牌/本地 B 端、节日/桌宴策划按次等，不进当前主排期（聚会收口与节日延后后，按次更靠后）。

### 一、一句话定位

用户站在菜场里，打开「买菜做什么」，确认今天可选食材；结合每人口味与忌口、菜式品类偏好、饭菜类型（日常 / 聚会）、想做几顿，以及最近吃过的菜，推荐“今天买哪几样 + 回去做什么菜”。

### 二、核心用户场景

**主场景**：
1. 用户走进菜场，打开小程序。
2. 系统弹出待确认的近期推荐菜（已与锚点之后已记录去重），**默认不勾选**，用户自行勾选吃过的；点确认或跳过后，**下次进菜场不再弹**同一批。
3. 确认今天可选食材：主列表只展示**时令菜**（按城市，默认全选，每类/整页有上限）；**四季常见主料**（如鸡蛋、猪肉、小白菜、番茄、鸡肉、北豆腐等，见内置数据）默认算已有，不铺在主列表，可点开「四季常见」取消今天没有的；调味常备不出现。可**手动补菜**。语音补菜 / 拍照识菜后置（入口未展示前不打对应埋点）。
4. 用户选择饭菜类型：**日常**或**聚会**。日常带出成员派生的大/小/老与默认可改荤素汤，再选几顿（可分午/晚）。聚会只用大/小/老设本场人数（不预填）、勾选本场忌口；**不露出荤素汤选择**，搭配由系统按人数规则自动生成（见模块 4）；几顿默认 1 顿、不区分午晚。
5. 系统结合**每位成员**（及当次访客）的年龄段 / 口味 / 忌口与已确认饮食记录，给出菜谱方案；用户可「换一批」。每个方案右侧有「去买菜」，点中后自动进入该方案的**购买食材页**；推荐卡上不提供「只看清单」入口。
6. 做完饭后，用户通过手动 / 语音自行记录吃了什么（拍照记录后置；不做自动记录）。

**关键约束**：
- 推荐结果必须**避开已确认吃过的菜**（近期确认弹层 + 历史记录）。
- 忌口分两层：**家庭忌口**硬排除；**成员忌口**按占比软约束（不因一人忌口清空所有相关菜），细则见模块 2 / 4，完整比例算法后续细化。
- 日常用画像忌口，带出成员大/小/老与**可改**默认搭配；聚会用本场大/小/老 + **本场忌口**硬排除，搭配**自动生成且页面不编辑**，不写回画像。
- 最终搭配以用户当次确认值为准。
- 用户不需要输入“我想吃什么”，系统主动给出方案。

### 三、功能模块

#### 模块 1：菜场输入与当次场景

**目标**：快速确认“今天可选食材”，并设定这一次要做几顿、什么场合、怎么搭配。

**食材确认方式**：
1. **四季常见主料**：一年到头菜场几乎都有的主料**默认计入已选**，主列表不展示；折叠「四季常见 · 已计入 N 样」，今天缺货可点开取消。当前内置含：鸡蛋、猪肉、土豆、洋葱、小白菜、菜心、芹菜、生菜、胡萝卜、莲藕、红薯、番茄、黄瓜、茄子、青椒、冬瓜、鸡肉、牛肉、鸭肉、四季豆、金针菇、香菇、北豆腐、豆干等。推荐与购买清单都认这份已选（未取消 = 场内已有）。
2. **时令菜列表（主力）**：季节性更明显、需用户扫一眼确认的主料（当前内置如菠菜、白萝卜、羊肉、毛豆及水产等），分类展示，**默认全选**；每类约 6～10 条、整页约 40～70，超出按常见度截断。可取消、可补菜。
3. **调味常备**（盐、生抽、葱姜蒜等）：确认页不出现，也不当作已选主料（菜谱允许缺调味）。
4. **拍照识别（辅助，后置）**：拍摊位照片识菜。当前确认页**不展示**入口。
5. **语音补菜（后置）**：说出菜名，转写后提取菜名让用户确认并入已选；MVP 入口不展示。

**食材数据来源**：
- 内置常见菜品库（兜底）。
- **美团外卖 / 买菜侧超市菜品抓取**：按城市日更；写入库可以多，**提权进时令主列表要抢名额**，不能抓到什么就铺在确认页。
- **（未来）线上商超 SKU 直连**：用户可选盒马等商超，以在售 SKU 作为推荐输入，见「八、未来需求点」。

**当次场景设置**（确认食材前后均可，建议同页或下一步）：
- **饭菜类型**：**日常** / **聚会**（亲戚/朋友/节日不再并列分叉出菜）。**节日选择暂时隐藏**，后续有需要再做。
- **人数与搭配**：
  - **日常**：大/小/老由成员派生，可按档加减访客；**荤素汤可改**，确认使用可写回默认。
  - **聚会**：只拨本场大/小/老（初始 0）；**不露荤素汤**；`combo` 自动生成（§下「聚会自动搭配」）；人数与搭配不写回画像。用餐人按档位默认偏好（大正常；小/老清淡）。
- **忌口**：日常用家庭忌口 + 成员软降权；聚会用**本场忌口**硬排除（不写回），软分仅本场档位默认用餐人。
- **想做几顿**：日常为快捷芯片（一顿晚饭 / 一顿午饭 / 1午+1晚）+ **自定义弹窗**（下半屏居中卡片；午/晚各 0～7，合计 ≤14；确认后芯片显示如 `2午+1晚`）；未选满顿数时提示「请先选择吃几顿」。聚会默认 1 顿「本场」，只调顿数、不选午晚。细则见 [`2026-10-11-日常几顿快捷与自定义-design.md`](../docs/superpowers/specs/2026-10-11-日常几顿快捷与自定义-design.md)。
- 场景页**不**让用户先点「今天吃火锅 / 面条 / 水饺」。主路径仍是确认食材与搭配；非常规餐由推荐按画像给出（见模块 4）。

**输出**：可选食材列表 + 当次场景参数，进入推荐。

#### 模块 2：用户画像（按人）

**目标**：让推荐符合家庭整体硬约束与成员差异，并记住日常默认搭配、菜式品类偏好与大致用餐时间；账号侧提供可编辑的展示资料。

**账号与「我的」展示资料（自建，非微信资料）**：
- **账号模型（概述）**：业务主键为 **uid**；登录方式通过 **`user_identities`** 多身份绑定（如小程序微信、日后 App 微信、手机号），互不覆盖。端类型（小程序 / iOS / Android）记在会话与埋点上，不作为用户唯一类型。细则见详细设计。
- **登录**：微信静默登录识别用户；**不**自动拉取微信昵称、头像。
- **默认昵称**：新用户自动生成 **`大厨` + 4 位字母数字短码**（如 `大厨K2M8`）；短码由账号标识派生，碰撞则加长。
- **默认头像**：使用产品内置占位图。
- **可修改**：在「我的」页可自行改昵称、更换头像（上传或选择）。
- **手机号**：支持在「我的」中**选填**并写入身份绑定；MVP 可不做短信验证。后期可升级为验证绑定，并按功能门槛强制补填（用于跨端统一账号等）。
- 「我的」页顶部展示：头像 + 昵称；其下为手机号（若已填，可脱敏）、家庭与画像设置入口等。

**家庭与成员**：
- 家庭可添加多名成员（本人、配偶、孩子等）；**「我的」须支持成员列表的增删改**（不仅引导时建「本人」）。
- **人数唯一来源 = 成员列表**：日常默认人数 = 成员数；摘要展示 `共 N 人 · x大 y小 z老`（映射见下）。**不再单独维护可编辑的「默认人数」**（`defaultPeopleCount` 仅作同步缓存 = N）。

**大 / 小 / 老（展示与推荐用，不改荤素汤份量）**：
- **小**：年龄段 `5_15`（5–15 岁）。**不做学龄前（5 岁以下）**——该年龄饮食需特殊处理，不在菜谱推荐范围内。
- **老**：`60_plus`。
- **大**：`16_25` / `26_40` / `41_59`。

**家庭忌口画像（整户硬约束）**：
- 单独维护一份**家庭忌口**（多选词表：猪肉类、海鲜、内脏、香菜、花生、乳制品等；如回民不吃猪肉勾「猪肉类」）。
- 推荐时：**只根据菜谱包含的食材**是否落在忌口大类上硬排除，**不靠菜名**（五花肉/排骨等同属猪肉类一并排除）。

**家庭菜系偏好**（与忌口、菜式形态品类并列）：
- 家庭级多选：各菜系标 **喜欢 / 一般 / 讨厌**（未设视为一般）；喜欢与讨厌互斥。
- **讨厌**的菜系：推荐硬排除带对应 `cuisineTags` 的菜；**喜欢**则软加权；菜谱无菜系标签不因菜系消失。
- 城市仍只决定当地常见食材列表；编辑城市旁提示「仅用于匹配当地常见食材」。

**成员级信息（按人独立，须采集并参与推荐）**：
- **年龄段**（单选，仅五档）：`5_15` / `16_25` / `26_40` / `41_59` / `60_plus`
- **口味**（清淡 / 正常 / 重口 / 嗜辣）——参与软排序
- **个人忌口**（多选，词表同家庭忌口）——**仅降权、不硬删**（避免一人不吃海鲜全家永远无海鲜）
- 「我的」每位成员约 3～4 个字段即可完成设置；引导可「再加一位」。

**当次临时加减人数（日常确认页，操作要简单）**：
- 展示与档案一致的大/小/老；提供**三档步进**（不是只拨总人数）。
- **+1 某档**：增加一名**本次访客**（不写 `members`）；该档自带默认偏好——大：口味正常、无忌口；小/老：口味清淡、无忌口，并参与少辣/少重口软降权。
- **−1 某档**：先减该档本次访客；不删已保存家人。
- 永久加人：走「我的 → 添加家人」。

**成员忌口占比规则（完整算法后续细化）**：
- MVP：**家庭忌口硬排除 + 成员/访客忌口排序降权 + 小/老对辣/重口软降权 + 口味软匹配**。
- 完整占比配额（按持有人数比例限制含忌口食材的菜占比）列入后续细化。

**菜式品类偏好**（与口味、忌口、几荤几素搭配并列的独立维度）：
- 描述「爱吃 / 常做 / 少做」的餐食形态，**不是**咸淡辣，也**不是**忌口，也**不是**菜系。
- 细分两类（多选，可标偏好强度：爱吃 / 一般 / 少做）：
  - **菜式形态**：热炒、凉菜、卤菜、火锅、汤羹、蒸菜、烧烤等
  - **主食形态**：米食、面食、粥粉、饼类等
- 归属建议：默认挂在**家庭级**（一家常做哪些品类）；若成员差异大，可按人覆盖（如某人不吃火锅则对该人降权，不上升为家庭忌口除非写入家庭忌口）。
- **面食**在画像里作一项（`noodle`）：爱吃时，推荐可出面条局或水饺局；少做则两类都少出。水饺在菜谱上用独立 tag `dumpling`，不必让用户再勾一层。

**菜系偏好**（家庭级，与品类独立；细则见 [`2026-10-12-家庭菜系偏好与城市提示-design.md`](../docs/superpowers/specs/2026-10-12-家庭菜系偏好与城市提示-design.md)）：
- 描述爱吃 / 一般 / 讨厌哪路菜（川、粤、湘、本帮等）；**只影响推荐出菜**，**不**改城市食材列表（菜场卖什么仍由城市决定）。
- 填写：默认全「一般」；多选「喜欢」与「不太做的」（互斥）；引导保留一步（可跳过）；「我的」可改。
- **讨厌 = 硬排除**带该菜系标签的整道菜；喜欢 = 加权。词表英文 code；**家常不对用户展示**。
- 本期仅家庭一份，不做成员级菜系。

**整户或账号级信息**：
- **人数**：由成员列表派生（见上）；日常场景带出大/小/老，可当次按档改
- 做饭时间预算（15 分钟内 / 30 分钟左右 / 1 小时以上）
- **一般几点吃饭**（如午饭 12:00、晚饭 18:30），方便后续推送“该记录了吗”之类提醒
- **默认搭配**（用户可自定义）：一荤一素、一荤两素、一荤一素一汤等；选日常时自动带出。**全户一份，不按午饭/晚饭分设**；**不**随大/小/老自动改份量。日常午/晚由当次「想做几顿」指定。聚会不区分午晚。
- **菜式品类偏好**（见上；家庭默认一份，成员可覆盖）
- **菜系偏好**（见上；仅家庭）
- **城市**：影响当地常见食材；编辑时提示「仅用于匹配当地常见食材」

**收集时机**：
- 首次进入即可用默认昵称/头像；首页可提示完整引导，允许「先逛逛」跳过。
- **日常轻量补全弹层**（见下）：用户选日常并确认食材后，若家庭忌口仍空，弹出可取消的短表，填忌口（必显）与「爱吃什么」（可选，如火锅、面食）；保存或跳过均进入推荐，**不挡首次出方案**。
- 完整引导（成员、用餐时间、默认搭配、城市、**菜系偏好**等）仍走 onboarding /「我的」；人数与搭配以当次场景页为准，**轻量弹层不再问**（菜系亦不进轻量弹层）。

**日常轻量补全弹层**（确认食材之后、出推荐之前）：
- **触发**：`mealType === 日常`，且 `familyAvoids` 为空（或等价「尚未补过家庭忌口」）；聚会不弹。
- **内容（宜少、宜快）**：
  1. **家庭忌口**：短列表多选（常见项；可「更多」展开），保存即写 `users.familyAvoids`，当次推荐立即按硬排除生效。
  2. **爱吃什么（可选）**：多选「火锅」「面食」等；勾选则对应 `dishFormPrefs` 记为 `prefer`，未勾保持 `neutral`。用于日后更容易出非常规方案，非必填。
- **不收**：人数、搭配、成员、用餐时间、城市、做饭预算（场景页或「我的」已有/稍后填）。
- **按钮**：主按钮「保存并看方案」；次要「暂时跳过」。跳过也 `navigate` 推荐页，当次按无忌口/中性品类出菜。
- **频控**：保存或跳过任一后，**本用户不再因同一条件反复弹**（可记 `profileLitePromptedAt` 或视「已跳过轻量补全」）；完整引导与「我的」仍可改。
- **文案取向**：说明「填忌口可少推不能吃的；可跳过，不影响本次出方案」。

#### 模块 3：饮食记录

**目标**：记住“最近吃过什么”，作为推荐排除项；记录全部由用户主动完成。

**记录方式**：
- **手动记录**：从历史推荐里选，或手动输入菜名。
- **拍照记录**：拍成品菜照片，识别或标注后存档（后置，入口**不展示**）。
- **语音记录**：说出吃了什么，转写后确认写入。
- **删除**：历史 / 记录列表中可**按条删除**已吃记录（纠正误记）；删除后不再参与近 7 日推荐排除与新鲜度。细则见饮食记录详细设计 §4.2。
- 不做自动记录；采纳推荐不会自动写入饮食记录。

**进入菜场输入时的确认弹层**：
- 进入菜场输入流程时，弹出待确认列表（有未处理锚点才弹），**默认不勾选**，用户勾选吃过的再提交。
- **去重**：列表须排除「近期已记录」中已有的菜（含在「已选方案」里点选标记的），**已标记的菜不展示**；若滤完后没有可确认的菜 → **不弹层**。
- **「近期已记录」口径**：以**最近一次采纳或有效停留（推荐页可见 ≥30 秒）之后**写入的饮食记录为准；更早的记录不纳入本次去重。若从未采纳且从未有效停留，**不弹**进场确认层。
- **确认或跳过一次即收口**：无论勾选后点确认，还是点跳过，都将该锚点标为已处理；**下一次再进菜场不再弹出**。仅当之后又有新的采纳/有效停留时才可能再弹。
- 用户确认勾选结果写入饮食记录（跳过则不写菜），再继续食材输入。

**已选方案历史（回顾 + 点选已吃）**：
- 用户点「去买菜」后，该次采纳写入推荐会话（时间、场景、所选方案）；可在 **「我的 → 已选方案」** 按时间倒序回顾要做哪些菜。
- 列表每次加载 **7** 条，滑完再加载更早的 7 条。
- 卡片内菜前勾选（样式同进场确认）：**点选即记为已吃，再点取消**；无单独提交按钮。列表顶长期小字说明点选/反选；**首次**进入该页另出悬浮气泡（只一次）。
- 细则见推荐详细设计 §3.3.1、饮食记录 §4.3；设计摘要 `2026-10-09-已选方案历史与点选已吃-design.md`。

**数据结构**：
- 每条记录：日期、餐次（午 / 晚等）、菜名、主要食材、记录来源（手动 / 拍照 / 语音 / 进场确认 / 已选方案点选）；若由某次搭配关联产生，保留对应 `recommendationId` / 搭配会话 id，便于界定「最近一次搭配之后」。
- 推荐时读取最近 7 天（可配置）已确认记录：**相同菜名硬排除**；主料重叠按 **分档 + 时间衰减** 加软惩罚（**分越高越靠后**），不因共用土豆等整类不推。细则与例子见推荐详细设计 §3.0.4。

#### 模块 4：推荐引擎

**目标**：根据可选食材、当次场景与每人画像，给出购买清单与多顿菜谱方案。

**搭配来源**：
- **日常**：进入当次场景时带出成员派生的大/小/老 + 默认搭配；人数可按档临时加减（访客不落库）；搭配可改；若到推荐页仍为空则提示补选，补选 / 确认后可写回默认搭配（人数写回规则：仅当未使用临时访客、且用户明确保存家庭时——默认**不**因临时加减改成员表）。
- **聚会**：大/小/老从 0 拨；`combo = suggestPartyCombo`（自动，页上不改）；本场忌口照常；不写回画像。
- 日常若推荐页仍无搭配：本页补选。聚会不走「补选荤素汤」。

**聚会自动搭配**（`suggestPartyCombo`，细则见菜场场景 §3.2.1）：
- `n = 大+小+老`；`meat = max(1, ⌊n/2⌋)`；**无小孩时 `meat += 1`**（加在荤上，不是加素）。
- 总菜数：有小孩 → `total = n`；无小孩 → `total = n + extra`，`extra` 为 **1 或 2**（按会话种子稳定随机，同 `requestId` 不变）。
- `soup = n≥2 ? 1 : 0`；`veg = total - meat - soup`，保证 `veg ≥ 1`。
- 小/老只影响软分（少辣/清淡），不再单独改结构。

**推荐逻辑**：
1. **过滤**：日常家庭忌口硬排除；聚会本场忌口硬排除。**家庭菜系讨厌**：菜谱 `cuisineTags` 与家庭 `avoid` 有交集则硬排除（家常与非常规均适用）。软分用餐人：日常 = 成员+访客；聚会 = 本场档位默认。新鲜度等见 §3.0.4 / §3.0.8。
2. **组合**：按 `scene.combo` 凑荤素汤（日常可手改；聚会为自动结果）；多顿拆顿；面/饺/火锅不进家常 combo；画像 prefer 时可出至多一套非常规。
3. **打分**：口味/小老/忌口软分、品类、**家庭菜系喜欢**软加权、新鲜度等；家常软惩罚越高越靠后。
4. **组合多样性（首次进入也要变）**：同食材、同场景下，**每次新开推荐会话**的家常/非常规方案组合应有可感知变化，**不能**总是同一批菜；不依赖用户先点「换一批」。仍须尊重过滤与软排序（忌口/新鲜度差的菜不能因「随机」冒到前面）。细则见推荐详细设计。
5. **输出**：1-3 个方案，每个包含：各顿菜名、简要做法（可选折叠）、人数与类型说明。其中最多 1 套为非常规（其余仍是家常炒菜汤）。
6. **同一套方案内去重**（组家常方案时边选边生效；与「多方案之间」不同）：
   - 硬约束（不够数也**不**放宽）：已用 `recipeId` → 归一化菜名相同 → **主料集合完全相同**（调味不参与；如土豆烧牛肉与土豆炖牛肉）→ 近义菜名（去掉烧/炖/炒等烹法词后相同）。
   - 软偏好：尽量避开本方案已用主料；仅此项可在候选不足时放宽。
   - 细则与过滤顺序见推荐详细设计 §3.0.7。
7. **多方案之间菜名重复上限**（同一次展示的家常方案两两比较；能少重复更好）：
   - 单套菜道数 **少于 5**：任意两套之间 **不允许** 相同菜名（同 `recipeId` / 归一化菜名）；
   - 单套菜道数 **≥ 5**：任意两套之间相同菜名 **最多 1 道**；
   - 单套菜道数 **≥ 8**：任意两套之间相同菜名 **最多 2 道**；
   - 候选不足以同时满足搭配结构与上述上限时：优先保证能凑齐 combo / 仍有方案可展示，再尽量压低重复；**不**为此清空结果。细则见推荐详细设计 §3.0.6。
8. **方案卡片与清单入口**：
   - **方案卡片上**：菜名下不再跟食材；**右下角一行** `食材：猪肉、豆腐等2种`（每道菜取 1 个主料名去重；优先更可能还要买的）。**不**展开完整清单与调味，也不设「查看购买清单」，避免不点「去买菜」。
   - **完整购买清单**：仅经「去买菜」进入购买食材页后展示。

**购买食材页（清单）**：
- 汇总当前采纳方案所需购买的食材（主料+调味去重）。
- **按食材分类分组**（肉类、叶菜、调味等）；组内**每行 2 个**食材，可勾「已买」（方便按摊位采购）。
- **不**展示「场内已有 / 主料 / 调味」等条目说明标签。
- **底部可点开菜谱弹层**：按菜展示本方案菜谱；菜名右侧列该菜食材（主料在前、调味在后；主料中肉类在前、非肉在后）。弹层**高度不超过半屏**、内容区可滚；打开时背后清单不可滚；右上角关闭或**点遮罩外**关闭。同页再次打开保持滚动位置，离开购买食材页则重置到顶部。细则见推荐详细设计 §4.4。

**菜谱数据来源**：
- 初期内置 JSON 菜谱库（200-500 道家常菜）：菜名、主食材、调味品、荤素、口味、**菜式品类**（菜式形态 + 主食形态标签）、耗时、适合人数。
- 后续可接 AI，初期以结构化数据保证稳定。

#### 模块 5：反馈与迭代

- 用户可对某一方案点「去买菜」采纳，或点「不行」；另有「换一批」。
- **换一批**：随便换菜看看；当次排除已展示菜并重跑；**不**作长期降权。
- **不行**：明确拒绝；**弹出原因面板**（不想吃 / 食材不对 / 太麻烦 / 最近吃过），**可不选**直接跳过；无论是否选原因都记 reject 并长期降权，通常随后换一批。
- **凑不出方案（重要）**：不要整页换成「空结果页」；确认页与推荐页用**同一套**窄居中弹窗。  
  - **确认食材页**点确认后若 `create` 凑不出：留在本页立刻弹窗，标题「食材不够出菜了」，无正文，「好吧」浅底色关闭；**不**跳转推荐页、**不**写入空会话。  
  - **推荐页**点「换一批 / 不行」后若凑不出新方案：**保留当前方案**，弹同一款窗；**不**清空方案、**不**跳转、**不**整页空文案。
- **点「去买菜」**（挂在**该方案右侧**，非页底全局按钮）：明确采纳对应 `planIndex` 的方案，并**自动跳转购买食材页**，方便在菜场对照采购（文案强调「去买」，避免被理解成纯确认）。不使用页底单独的「可以」，以免多方案时分不清选的是哪一套。  
  - **未来**：若对接买菜 / 商超平台，同一按钮可扩展为跳转外链并把清单带过去加购；当前仍先进本小程序清单页。
- **不提供**「查看购买清单」预览入口：进清单只有「去买菜」一条路，避免分流采纳。
- 上述信号用于调整后续推荐权重（reject ≫ swap）。

### 四、页面结构

> 流程图（含广告曝光位）见 [`doc/需求流程图.md`](./需求流程图.md)。

1. **首页**：入口「今天菜场有什么」；次要入口「记一下吃了什么」（手动 / 语音；拍照后置）。**字号切换也在首页**（见下「大字版」），不放进「我的」，避免年长用户多点一层。
2. **进场确认弹层**（进入输入流程时）：若有最近一次采纳或有效停留（推荐页 ≥30 秒）且**尚未处理过进场确认**的方案菜，展示并排除锚点之后已记录的菜（**已标记的不展示**；全已标记则不弹），**默认不勾选** → 用户勾选后确认，或点跳过 → **均标记已处理，下次进菜场不再弹**；无可用锚点则不弹。
3. **输入页**：
   - 时令常见菜主列表（默认全选，有上限）+ 四季常见默认计入（可展开取消）+ 手动补菜（语音补菜 / 拍照识菜后置）；
   - 当次场景：**日常 / 聚会**；日常带出大/小/老 + 可改荤素汤；聚会只拨大/小/老 + 本场忌口、**不露荤素汤**（自动 combo），几顿默认 1 顿；
   - 确认后：若为**日常**且家庭忌口仍空 → **轻量补全弹层**（忌口 + 可选「爱吃什么」，可跳过）→ 再 `create`；否则直接 `create`。**若凑不出任何方案：不进推荐页**，本页立刻弹与推荐页同款窗「食材不够出菜了」（见模块 5）。
4. **推荐页**：展示 1-3 个方案（含多顿拆分）；卡右下角一行食材摘要（如 `食材：猪肉、豆腐等2种`）；未选搭配则在此补选（日常可保存为默认）；底部「换一批 / 不行」；**每个方案标题右侧**有「去买菜」。点「去买菜」后**自动进入该方案的购买食材页**；采纳后**不自动记饮食**。换一批/不行若无新方案：弹窗「好吧」，**保留当前方案**（见模块 5）。
5. **购买食材页**：按分类展示要买的食材，每行 2 个，可勾「已买」；无已有/调味说明标签。底部可打开**菜谱弹层**（按菜+右侧食材）。仅从「去买菜」进入（`accepted=true` + 对应 `planIndex`）。**可返回推荐页换方案**；不另加「回首页」按钮（买完常直接退出小程序）。
6. **记录页 / 已吃记录**：手动、语音写入；拍照入口不展示；列表支持**按条删除**已吃。可从首页或「我的 → 已吃记录」进入。
7. **已选方案页**：从「我的 → 已选方案」进入；展示已采纳方案（时间、场景、菜名）；点选/取消已吃见上。
8. **我的页**：头像 + 昵称（默认「大厨xxxx」，可改）；手机号选填；家庭忌口、菜式品类偏好、**家庭菜系偏好**、**家庭成员列表（增删改：称呼 / 年龄段五档 / 口味 / 个人忌口）**与摘要 `N人·大/小/老`、默认搭配（**无独立默认人数编辑**）、用餐时间、做饭时间预算、**已选方案**、**已吃记录**、城市（旁注：仅用于匹配当地常见食材）。**不含**大字版开关（开关仅在首页）。

#### 大字版（无障碍字号）

**目标**：年长用户在首页一键放大正文与按钮字号，少走「我的」。

**交互**：
- 入口仅在**首页**（与「我的」同级可见，勿藏进二级页）。
- 当前为常规字号时，控件文案为 **「大字版」**；点按后全局进入大字档，控件文案变为 **「小字版」**（再点恢复常规）。
- 偏好**本地持久化**，下次冷启动仍生效；各页进入时同步当前档。

**实现要点**：
- 用全局字号令牌（如 `--fs-body` / `--fs-btn` / `--fs-title`），大字档只改令牌，不另做一套页面。
- 主路径挤布局（底部栏、chip、清单双列、悬浮钮）在大字档下允许略增高触控区；导航栏标题受系统限制可不放大。

### 五、技术实现提示（给 Cursor 的指令）

> 字段级与算法细则见 `docs/superpowers/specs/` 下技术设计概述及各模块「详细设计-*.md」（账号、画像、菜场输入、饮食记录、推荐、埋点、主数据）。

**技术栈**：
- 微信小程序原生开发（或 Taro / uni-app）
- 后端：微信云开发（云函数 + 云数据库）优先
- 数据库集合建议：
  - `users`：账号与家庭级设置（uid、nickname / avatarUrl、用餐时间、默认搭配、城市、做饭预算、家庭忌口、菜式品类偏好等）
  - `user_identities`：登录身份绑定（provider + 平台侧 id，如小程序 openid / App openid / 手机号）
  - `members`：家庭成员（年龄段、每人口味、个人忌口、可选品类偏好覆盖）
  - `ingredients`：常见 / 在售菜品（`cities[]`；`kind` 主料/调味；`availability` 四季/时令；`onConfirmPage`；来源、更新时间）
  - `ingredient_sync_jobs`：美团侧抓取任务状态（任务目标城市、日期、成功条数）
  - `recipes`：菜谱库（含 `dishForms` / `stapleForms` 品类标签、`cities[]`）
  - `meal_logs`：饮食记录（仅用户确认或主动记录后写入）
  - `recommendations`：推荐历史与反馈（含「换一批」）
  - `holidays`：按年打包的节日日历（`year` + `items`：日期、中英文名、稳定 id；供节日聚会推送）

**关键实现点**：
1. **默认菜列表**：按 `users.city` 读 `ingredients`。接口返回时令主列表 + 四季常见；进入页**只全选时令主列表**；四季常见默认计入已选但不铺开。无城市数据时回退全国项。长尾与调味不进主列表。
2. **菜品日更**：云函数定时任务，试点城市 = 省会 + 直辖市；写入 / 更新 `ingredients`（注意合规与风控：频率、字段最小化、失败重试与人工兜底库）。
3. **推荐引擎**：云函数纯规则引擎优先；输入 = 食材 ∩ 场景 ∩ **家庭忌口硬排除** ∩ **菜系 avoid 硬排除** ∩ **成员/访客忌口降权** ∩ **口味与小/老软降权** ∩ 菜式品类 / **菜系 prefer** 加权 ∩ 近 7 日 `meal_logs`。成员忌口占比配额后续细化。**桶内按会话种子做稳定旋转**。细则见推荐与用户画像详细设计。
4. **人数 / 搭配预填与推荐**：
   - `mealType === 日常`：人数与大/小/老由 `members` 派生；场景可带 `guestCounts`（临时访客）；`defaultCombo` 预填可改；采纳写回**搭配**时勿把临时访客写入成员表。
   - 聚会：大/小/老初始 0；`suggestPartyCombo` 自动写 `combo`（无小孩荤+1；总菜 n 或 n+1~2 种子随机）；不露搭配编辑；`partyAvoids`；禁止写回（见菜场 §3.2.1）。
5. **菜式品类**：画像存 `prefer` / `neutral` / `avoid`；`prefer` 加分并可触发对应非常规方案，`avoid` 降权且不出该类非常规方案（未写入家庭忌口则不从家常池硬删）。菜谱入库必须带品类标签。
6. **饮食记录**：禁止在「采纳推荐」时自动写 `meal_logs`；写入入口为：进场确认弹层、**已选方案点选（`plan_ate`）**、手动、语音（拍照后置）；已吃列表可按条删除。
7. **进场确认**：锚点 = 最近一次 `acceptedAt` 或 `engagedAt`（可见≥30s）取更晚者，**只看这一条、不往前翻**；该条已 `entryConfirmHandled` 或候选空则不弹。候选 = 锚点 plan 菜 − 「近期已记录」（含 `plan_ate`）；**已标记菜不展示**。弹层**默认不勾选**；确认（含勾 0 道）或跳过均写 `entryConfirmHandled=true`；勾选的菜批量写 `meal_logs`。
8. **已选方案历史**：`recommend.listAccepted` 分页 7；点选/取消走 `meals.planAteOn` / `planAteOff`（一道菜一条日志）。
9. **换一批 / 不行**：`swap` 仅当次排除已展示菜；`reject` 弹原因面板（可不选）并长期降权，与 swap 分记。凑不出新方案时弹窗「好吧」并保留当前方案（不切空页）；首次 create 空结果则留在输入页弹窗。
10. **购买食材页**：由方案菜谱聚合去重生成清单；按 `category` 分组，每行 2 个勾选；不展示已有/主料/调味标签。底部菜谱弹层按菜展示食材顺序（主料→调味，肉→非肉）；滚动位置仅在本页会话内保持。点方案旁「去买菜」→ `accept` 带 `planIndex` → `navigateTo` 食材页并标记 `accepted=true`。
11. **用餐时间**：用成员 / 家庭配置的午饭晚饭时刻，后续可做订阅消息提醒「记一下今天吃了什么」（提醒本身可放后期）。
12. **菜谱库**：初期目标 **200～500** 道家常菜 JSON 入库（与模块 4 一致；结构正确优先）；与多顿、几荤几素、菜式品类标签对齐；带 `cities[]`（空=全国）；须含火锅 / 面条 / 水饺样本；每道菜拆主料 / 调味便于清单排序。

### 六、最小可行版本（MVP）范围

第一版只做：
- 时令常见菜主列表 + 全选确认（有上限）；四季常见默认计入可取消；**手动补菜**
- 当次场景：日常 / 聚会；聚会不露荤素汤、自动 `suggestPartyCombo`；本场忌口；几顿默认 1 顿
- 微信登录 + 默认昵称「大厨xxxx」与默认头像（可在「我的」修改）；手机号选填
- 按人画像：「我的」可管多名成员（年龄段五档、口味、个人忌口）；家庭：家庭忌口（硬排除）、菜式品类偏好、默认搭配；人数由成员数派生
- 推荐：家庭忌口硬排除；成员/访客忌口 + 口味 + 小/老软降权；菜式品类按画像加权；可出火锅 / 面条 / 水饺非常规方案（至多一套）
- 进场确认近期是否吃过（默认不勾选；确认或跳过后下次不弹；锚点为采纳或推荐页停留≥30s；无可用锚点不弹）
- 日常确认食材后：忌口未填则轻量补全弹层（忌口 + 可选「爱吃什么」，可跳过，不挡出方案）
- 规则引擎推荐 + **组合多样性（新会话即变）** + **同方案内去重** + **多方案菜名上限** + **换一批**
- 方案旁点「去买菜」自动进该方案购买食材页（按分类、每行 2 个）；底部菜谱弹层可查每菜食材；无「查看购买清单」预览入口
- **已选方案历史**（分页 7）+ 点选/取消已吃；进场确认不展示已标记菜
- 手动 + **语音**记录饮食；已吃列表可按条删除（删除 UI 可与本切片同做或紧随）

**不做 / 可延后**：
- 成员忌口的完整占比配额与小样本取整策略（先降权）
- 美团菜品抓取日更（可先用静态城市菜列表；接口与表结构先预留）
- **线上商超接入推荐**（见「八、未来需求点」；MVP 仅线下菜场 / 静态列表）
- 拍照识别食材、**语音补菜**、拍照记饮食（入口不展示，实装后再放出；对应埋点入口未展示前不打）
- AI 生成菜谱
- 社区、分享、排行榜
- 用餐时间订阅消息推送

### 七、验证指标

- 用户是否在菜场完成「确认食材 + 场景」并看到推荐
- 「进场确认吃过」的完成率与勾选比例（勾选数 / 候选数）
- 用户是否主动完成饮食记录（手动 / 语音）
- 「换一批」点击率与采纳前平均换批次数
- 点「去买菜」后进入食材页的比例
- 7 天内回访率
- 日常默认搭配被复用的比例

### 八、未来需求点

#### 8.1 线上商超接入推荐

**诉求**：除线下菜场「确认今天有什么」外，用户也可**接入线上商超**，用商超在售 / 可加购 SKU 作为「今天可选食材」来源，再走同一套画像与推荐引擎，尤其适合 **盒马** 等 SKU 特别丰富的商超（品类细、预制与生鲜并存，比传统菜场列表更能撑起多样化搭配）。

**示意能力**：
- 用户选择渠道：线下菜场（现状） / 指定线上商超（如盒马，后续可扩美团买菜、叮咚等）。
- 拉取或同步该商超当前可售 SKU（需官方合作或合规接口；按门店 / 配送范围过滤）。
- 推荐与清单基于商超 SKU 生成；购买食材页可导向商超加购 / 下单（与盈利方案中的分佣候选衔接，仍非 MVP）。
- 与现有流程兼容：进场确认、忌口、搭配、多顿、换一批逻辑复用；仅「可选食材」数据源切换。

**为何后置**：依赖商超开放能力与门店库存实时性；SKU 映射到菜谱主料需要品类对齐；合规与商务周期长。当前以线下菜场 + 静态 / 日更常见菜列表验证推荐闭环即可。
