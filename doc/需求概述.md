## 产品需求文档：做什么菜 / cookthis（微信小程序）

### 产品名称

| 语言 | 名称 | 用途 |
|------|------|------|
| 中文 | **做什么菜** | 微信小程序展示名、用户可见文案 |
| 英文 | **cookthis** | 工程名、仓库名、技术标识 |

> 一句话：站在菜场里，打开「做什么菜」，告诉它今天有什么，它告诉你回去做什么。

### 市场突破点

相对下厨房、美团买菜菜谱、各类「今日吃什么」工具，本产品的切入点不是「先想好吃什么再找做法」，而是**站在菜场决策现场**：用「今天有什么」倒推出「买哪几样 + 回去做什么」。

1. **场景卡位：菜场即时决策**  
   用户痛点发生在摊位前（时间紧、选择多、怕买多买重）。小程序服务「确认在售食材 → 出方案 → 出购买清单」闭环，比回家后再翻菜谱更贴决策瞬间。

2. **供需反转：有什么 → 做什么**  
   默认确认时令常见菜（全选、有上限）；四季常见主料默认计入但不占主列表；再结合人数、搭配、几顿饭出推荐。

3. **家庭真实约束，而不只是个人口味**  
   家庭忌口硬排除、成员忌口占比软约束、菜式品类偏好、避开近期已吃过——解决「一人决定全家吃腻 / 踩雷忌口」的家常难题，聚会与日常场景分流。

4. **一次买多顿，清单可执行**  
   支持「想做几顿」规划，点「可以」直达购买食材页（主料优先、调味靠后），把推荐落到菜场可勾选的采购动作，而不是停在菜名列表。

5. **微信搜一搜天然关键词**  
   产品中文名即高频生活问句「做什么菜」，利于搜一搜 / 小程序名匹配与内容种草；配合进场确认饮食记录，形成「用一次 → 记一次 → 下次更准」的留存钩子。

### 关键词热度备忘（微信指数）

**查询说明**：微信内搜「微信指数」小程序；指数为生态综合热度（搜一搜 / 视频号 / 公众号等），≠ 纯搜索量。

|--------|-----------|--------|------------------------------|
| **吃什么菜** | **76,886** | -5.97% | 基线约 9万–12万；月末峰值约 26万级，整体热度稳定偏高 |
| **做什么菜** | **785** | +11.35% | 多数时间接近底部；约 9/3–9/15 冲高（峰值约 6万–7万）后回落 |

**对比结论**：同日「吃什么菜」指数约为「做什么菜」的 **~98 倍**（76886 / 785），搜一搜侧前者明显更热。

**命名决策（暂定）**：
- **展示名仍用「做什么菜」**，不改为「吃什么菜」。理由：产品是菜场→采购→**做**饭闭环；「吃」更偏外卖/下馆子/今日吃啥的宽需求，热词流量与场景匹配度差，且竞争更挤。
- **流量侧借用热词**：小程序搜索关键词、简介、内容种草优先覆盖 `吃什么菜`、`今天吃什么` 等，与展示名分流（品牌名准、获客词热）。
- 英文工程名 **cookthis** 不变。
- 若上线后搜一搜转化差，再评估副标题或双名策略（如简介写「吃什么菜 · 菜场搭配」），而非立刻改掉主品牌名。

### 商业模式（摘要）

> 全文见 [`doc/盈利模式方案.md`](./盈利模式方案.md)。

- **最终路径**：**先广告、后会员**。流量主达标后，在购买食材页（用户**于摊位挑真菜、对照清单**时）放原生广告（日常 1 条；非日常清单更长可 2 条，不插屏），用收入支撑能力建设；有稳定使用数据后再上会员（去广告 + 多顿/聚会等增值）。  
- **主链路免费**：日常推荐与清单不设付费墙。  
- **候选保留**：电商分佣、品牌/本地 B 端、聚会按次等，不进当前主排期。

### 一、一句话定位

用户站在菜场里，打开「做什么菜」，确认今天可选食材；结合每人口味与忌口、菜式品类偏好、饭菜类型（日常 / 聚会）、想做几顿，以及最近吃过的菜，推荐“今天买哪几样 + 回去做什么菜”。

### 二、核心用户场景

**主场景**：
1. 用户走进菜场，打开小程序。
2. 系统弹出待确认的近期推荐菜（已与锚点之后已记录去重），**默认不勾选**，用户自行勾选吃过的。
3. 确认今天可选食材：主列表只展示**时令常见菜**（按城市，默认全选，每类/整页有上限）；**四季常见主料**（鸡蛋、猪肉、土豆等）默认算已有，不铺在主列表，可点开「四季常见」取消今天没有的；调味常备不出现。可补菜；**语音说出菜名**辅助补充。拍照识菜后置。
4. 用户选择饭菜类型：日常则自动带出默认人数与搭配（可改），再选想做几顿（可区分午/晚）；非日常不预填人数，填人数后系统给出推荐搭配，**几顿默认 1 顿可改、不区分午晚**；非日常另选忌口。
5. 系统结合每人画像与已确认的饮食记录，给出菜谱方案；用户可「换一批」。点「可以」后自动进入**购买食材页**；未点「可以」时，推荐页也有清晰入口可进入该页。
6. 做完饭后，用户通过手动 / 语音自行记录吃了什么（拍照记录后置；不做自动记录）。

**关键约束**：
- 推荐结果必须**避开已确认吃过的菜**（近期确认弹层 + 历史记录）。
- 忌口分两层：**家庭忌口**硬排除；**成员忌口**按占比软约束（不因一人忌口清空所有相关菜），细则见模块 2 / 4，完整比例算法后续细化。
- 日常场景用画像忌口，并**自动带出**默认人数与默认搭配（可改）；非日常不预填默认值，输入人数后系统给出**推荐搭配**（可改），当次忌口**不写入**日常偏好。
- 最终搭配以用户当次确认值为准。
- 用户不需要输入“我想吃什么”，系统主动给出方案。

### 三、功能模块

#### 模块 1：菜场输入与当次场景

**目标**：快速确认“今天可选食材”，并设定这一次要做几顿、什么场合、怎么搭配。

**食材确认方式**：
1. **时令常见菜列表（主力）**：按用户城市给出**时令**主料，分类展示，**默认全选**；每类约 6～10 条、整页约 40～70，超出按常见度截断。可取消、可补菜。
2. **四季常见主料**：一年到头菜场几乎都有的（如鸡蛋、猪肉、土豆、洋葱）**默认计入已选**，主列表不展示；折叠「四季常见 · 已计入 N 样」，今天缺货可点开取消。推荐与购买清单都认这份已选（未取消 = 场内已有）。
3. **调味常备**（盐、生抽、葱姜蒜等）：确认页不出现，也不当作已选主料（菜谱允许缺调味）。
4. **拍照识别（辅助，后置）**：拍摊位照片识菜。当前确认页**不展示**入口。
5. **语音输入（辅助）**：说出菜名，转写后提取菜名让用户确认并入已选。

**食材数据来源**：
- 内置常见菜品库（兜底）。
- **美团外卖 / 买菜侧超市菜品抓取**：按城市日更；写入库可以多，**提权进时令主列表要抢名额**，不能抓到什么就铺在确认页。
- **（未来）线上商超 SKU 直连**：用户可选盒马等商超，以在售 SKU 作为推荐输入，见「八、未来需求点」。

**当次场景设置**（确认食材前后均可，建议同页或下一步）：
- **饭菜类型**：日常饭菜 / 亲戚聚会 / 朋友聚会 / 节日聚会。
  - 节日聚会：系统自动推送近期节日供选择（如中秋、国庆、春节等）。
- **人数与搭配（随类型变化）**：
  - **日常**：自动带出画像中的**默认人数**与**默认搭配**，方便直接用；用户仍可修改。修改后的搭配若确认使用，可按模块 4 规则写回默认（仅日常）。
  - **非日常**：人数、搭配**不给默认值**；用户先输入人数后，系统按人数给出**推荐搭配**（如 2 人 → 一荤一素；4–6 人 → 两荤两素一汤等），用户可改；推荐搭配仅当次有效，不写回画像。
- **忌口**：
  - **日常**：使用画像中的**家庭忌口**（硬排除）+ **各成员忌口**（占比软约束），不在当次再选一遍。
  - **非日常**：当次可勾选本场忌口（视为本场「家庭忌口」硬排除）；成员忌口仍按画像做占比约束。当次选择不写回日常画像。
- **想做几顿**：日常例如「一顿晚饭」「两顿晚饭」，可区分午/晚，一次买齐多顿；**不指定用在哪一天**（用户自定）。**非日常默认 1 顿**，可改顿数，**不选午饭/晚饭**。
- 场景页**不**让用户先点「今天吃火锅 / 面条 / 水饺」。主路径仍是确认食材与搭配；非常规餐由推荐按画像给出（见模块 4）。

**输出**：可选食材列表 + 当次场景参数，进入推荐。

#### 模块 2：用户画像（按人）

**目标**：让推荐符合家庭整体硬约束与成员差异，并记住日常默认搭配、菜式品类偏好与大致用餐时间；账号侧提供可编辑的展示资料。

**账号与「我的」展示资料（自建，非微信资料）**：
- **账号模型（概述）**：业务主键为 **uid**；登录方式通过 **`user_identities`** 多身份绑定（如小程序微信、日后 App 微信、手机号），互不覆盖。端类型（小程序 / iOS / Android）记在会话与埋点上，不作为用户唯一类型。细则见详细设计。
- **登录**：微信静默登录识别用户；**不**自动拉取微信昵称、头像。
- **默认昵称**：新用户自动生成 **`大厨` + 4 位字母数字短码**（如 `大厨K2M8`）；短码由账号标识派生，碰撞则加长。
- **默认头像**：使用产品内置占位图。
- **可修改**：在「我的」页可自行改昵称、更换头像（上传或选择）。
- **手机号**：支持在「我的」中**选填**并写入身份绑定；MVP 可不做短信验证。后期可升级为验证绑定，并按功能门槛强制补填（用于跨端统一账号等）。
- 「我的」页顶部展示：头像 + 昵称；其下为手机号（若已填，可脱敏）、家庭与画像设置入口等。

**家庭与成员**：
- 家庭可添加多名成员（本人、配偶、孩子等）。

**家庭忌口画像（整户硬约束）**：
- 单独维护一份**家庭忌口**（多选词表：猪肉类、海鲜、内脏、香菜、花生、乳制品等；如回民不吃猪肉勾「猪肉类」）。
- 推荐时：**只根据菜谱包含的食材**是否落在忌口大类上硬排除，**不靠菜名**（五花肉/排骨等同属猪肉类一并排除）。

**成员级信息（按人独立）**：
- **年龄段**（单选，例：`0-2` / `3-5` / `6-15` / `16-25` / `26-40` / `41-60` / `60+`；具体枚举以实现与详细设计为准）
- 口味偏好（清淡 / 正常 / 重口 / 嗜辣）
- 忌口或过敏（多选：猪肉类、香菜、内脏、海鲜、花生、乳制品、其他）
- 说明：成员忌口**不能**简单取并集后清空所有相关菜（避免一人不吃香菜导致整桌无香菜菜）。处理见下方「成员忌口占比规则」。

**成员忌口占比规则（软约束，后续细化）**：
- 按「对某忌口项持有的人数 / 当次总人数」得到占比 \(p\)（例：5 人中 3 人不吃香菜 → \(p = 0.6\)）。
- 在一次推荐出的菜品集合中，含该忌口食材的菜占比应 **≤ \(1 - p\)**（上例香菜菜 ≤ 0.4）。
- 中国家庭人数与单次菜数都偏少，简单比例容易失真（如只推 2～3 道菜时 0.4 很难落地），故 **MVP 可先实现家庭忌口硬排除 + 成员忌口仅作排序降权**；完整占比配额规则列入后续细化。

**菜式品类偏好**（与口味、忌口、几荤几素搭配并列的独立维度）：
- 描述「爱吃 / 常做 / 少做」的餐食形态，**不是**咸淡辣，也**不是**忌口。
- 细分两类（多选，可标偏好强度：爱吃 / 一般 / 少做）：
  - **菜式形态**：热炒、凉菜、卤菜、火锅、汤羹、蒸菜、烧烤等
  - **主食形态**：米食、面食、粥粉、饼类等
- 归属建议：默认挂在**家庭级**（一家常做哪些品类）；若成员差异大，可按人覆盖（如某人不吃火锅则对该人降权，不上升为家庭忌口除非写入家庭忌口）。
- **面食**在画像里作一项（`noodle`）：爱吃时，推荐可出面条局或水饺局；少做则两类都少出。水饺在菜谱上用独立 tag `dumpling`，不必让用户再勾一层。

**整户或账号级信息**：
- 家庭默认人数（日常场景自动带出，可被当次修改）
- 做饭时间预算（15 分钟内 / 30 分钟左右 / 1 小时以上）
- **一般几点吃饭**（如午饭 12:00、晚饭 18:30），方便后续推送“该记录了吗”之类提醒
- **默认搭配**（用户可自定义）：一荤一素、一荤两素、一荤一素一汤等；选日常时自动带出。**全户一份，不按午饭/晚饭分设**；日常午/晚由当次「想做几顿」指定，各顿共用该搭配（可当次改）。非日常不区分午晚。习惯几点吃饭只用于提醒，不表示两套配菜。
- **菜式品类偏好**（见上；家庭默认一份，成员可覆盖）

**收集时机**：首次进入即可用默认昵称/头像；引导填写**家庭忌口**与**菜式品类偏好**，再建成员并逐人填口味 / 忌口（及可选的个人品类覆盖），再填用餐时间与默认搭配；昵称头像、手机号、画像后续均在「我的」里修改。

#### 模块 3：饮食记录

**目标**：记住“最近吃过什么”，作为推荐排除项；记录全部由用户主动完成。

**记录方式**：
- **手动记录**：从历史推荐里选，或手动输入菜名。
- **拍照记录**：拍成品菜照片，识别或标注后存档（后置，入口**不展示**）。
- **语音记录**：说出吃了什么，转写后确认写入。
- 不做自动记录；采纳推荐不会自动写入饮食记录。

**进入菜场输入时的确认弹层**：
- 进入菜场输入流程时，弹出待确认列表（有锚点才弹），**默认不勾选**，用户勾选吃过的再提交。
- **去重**：列表须排除「近期已记录」中已有的菜，避免与已记过的重复弹出。
- **「近期已记录」口径**：以**最近一次采纳或有效停留（推荐页可见 ≥30 秒）之后**写入的饮食记录为准；更早的记录不纳入本次去重。若从未采纳且从未有效停留，**不弹**进场确认层。
- 用户确认哪些确实吃过（可取消未吃的），确认结果写入饮食记录，再继续食材输入。

**数据结构**：
- 每条记录：日期、餐次（午 / 晚等）、菜名、主要食材、记录来源（手动 / 拍照 / 语音 / 进场确认）；若由某次搭配关联产生，保留对应 `recommendationId` / 搭配会话 id，便于界定「最近一次搭配之后」。
- 推荐时读取最近 7 天（可配置）已确认记录：**相同菜名硬排除**；主料有重叠则**降权**（不因共用土豆等整类不推）。

#### 模块 4：推荐引擎

**目标**：根据可选食材、当次场景与每人画像，给出购买清单与多顿菜谱方案。

**搭配来源**：
- **日常**：进入当次场景时自动带出默认人数 + 默认搭配，用户可改；若到推荐页仍为空则提示补选，补选 / 确认后可写回画像默认。
- **非日常**：不预填；用户输入人数后，按人数规则给出推荐搭配（可改）；仅当次生效，**不保存**到画像。
- 若推荐页仍未指定搭配：在本页提示补选（非日常可再次按人数推荐一版供选）。

**推荐逻辑**：
1. **过滤**：
   - **家庭忌口**（日常用画像；非日常用当次本场忌口）：按菜谱食材归属的忌口大类硬排除（不用菜名）。
   - **成员忌口**：不按并集硬删；按占比软约束或降权（见模块 2；完整配额后续细化）。
   - 排除近期已确认吃过的**相同菜名**；主料重叠只降权、不硬删。
2. **组合**：家常方案严格按用户指定的几荤几素几汤生成，并按「想做几顿」拆顿、避免撞菜。画像爱吃火锅 / 面食时，**额外可出至多一套非常规方案**（火锅、面条或水饺），与家常方案并列供选，不改变场景表单。
3. **打分排序**：食材匹配度、各成员口味匹配、**菜式品类匹配**（画像爱吃加权 / 少做降权）、新鲜度（同菜名已硬排除；主料近期重叠则降权）、时间预算匹配、人数是否够吃。非常规方案还看：人数、聚会类型、已选里是否已有涮品/面条/饺皮馅料、近 7 日是否刚吃过同类。
4. **输出**：1-3 个方案，每个包含：各顿菜名、简要做法（可选折叠）、人数与类型说明，以及对应的**购买食材清单**（详见食材页）。其中最多 1 套为非常规（其余仍是家常炒菜汤）。

**购买食材页（清单）**：
- 汇总当前采纳 / 查看方案所需购买的食材。
- **排序**：主要食材（肉禽蛋奶、蔬菜、水产等）靠前；调味品（盐、生抽、料酒、葱姜蒜等，若需单买）靠后。
- 可按顿次或按分类展示；已在「今天可选」里确认有的可标记为「场内已有 / 不用再买」，突出还需购买项。

**菜谱数据来源**：
- 初期内置 JSON 菜谱库（200-500 道家常菜）：菜名、主食材、调味品、荤素、口味、**菜式品类**（菜式形态 + 主食形态标签）、耗时、适合人数。
- 后续可接 AI，初期以结构化数据保证稳定。

#### 模块 5：反馈与迭代

- 用户可对推荐点「可以」或「不行」；另有「换一批」。
- **换一批**：随便换菜看看；当次排除已展示菜并重跑；**不**作长期降权。
- **不行**：明确拒绝；**弹出原因面板**（不想吃 / 食材不对 / 太麻烦 / 最近吃过），**可不选**直接跳过；无论是否选原因都记 reject 并长期降权，通常随后换一批。
- **点「可以」**：采纳当前方案，并**自动弹出 / 跳转购买食材页**，方便在菜场对照采购。
- **未点「可以」**：推荐页仍提供**清晰入口**（如「查看购买清单」），可进入同一食材页预览该方案要买什么，不视为正式采纳。
- 上述信号用于调整后续推荐权重（reject ≫ swap）。

### 四、页面结构

> 流程图（含广告曝光位）见 [`doc/需求流程图.md`](./需求流程图.md)。

1. **首页**：入口「今天菜场有什么」；次要入口「记一下吃了什么」（手动 / 语音；拍照后置）。
2. **进场确认弹层**（进入输入流程时）：若有最近一次采纳或有效停留（推荐页 ≥30 秒）的方案菜，展示并排除锚点之后已记录的菜，**默认不勾选** → 用户勾选后写入再进输入页；无锚点则不弹。
3. **输入页**：
   - 时令常见菜主列表（默认全选，有上限）+ 四季常见默认计入（可展开取消）+ 语音补充（拍照识菜后置）；
   - 当次场景：饭菜类型（含近期节日）；日常自动带出默认人数 / 搭配（可改），几顿可区分午晚；非日常不预填人数，输入人数后出推荐搭配，几顿默认 1 顿可改、不区分午晚；忌口（非日常）；
   - 确认后进入推荐页。
4. **推荐页**：展示 1-3 个方案（含多顿拆分）；未选搭配则在此补选（日常可保存为默认 / 非日常按人数推荐且不保存）；「换一批」「可以 / 不行」；每个方案旁有明确入口「查看购买清单」。点「可以」后**自动进入购买食材页**；采纳后**不自动记饮食**。
5. **购买食材页**：展示要买的食材；主料优先、调味品靠后；支持对照勾选「已买」。可从「可以」自动进入，或从推荐页入口进入。
6. **记录页 / 记录入口**：手动、语音写入；拍照入口不展示。可从首页或「我的 → 历史」进入。
7. **我的页**：头像 + 昵称（默认「大厨xxxx」，可改）；手机号选填；家庭忌口、菜式品类偏好、家庭成员管理（年龄段、每人口味 / 忌口 / 可选品类覆盖）、用餐时间、默认搭配、做饭时间预算、历史记录、城市（单个，影响默认食材与可见菜谱）。

### 五、技术实现提示（给 Cursor 的指令）

> 字段级与算法细则见 `docs/superpowers/specs/` 下技术设计概述及各模块「详细设计-*.md」（账号、画像、菜场输入、饮食记录、推荐、埋点、主数据）。

**技术栈**：
- 微信小程序原生开发（或 Taro / uni-app）
- 后端：微信云开发（云函数 + 云数据库）优先
- 数据库集合建议：
  - `users`：账号与家庭级设置（uid、nickname / avatarUrl、用餐时间、默认搭配、城市、做饭预算、家庭忌口、菜式品类偏好等）
  - `user_identities`：登录身份绑定（provider + 平台侧 id，如小程序 openid / App openid / 手机号）
  - `members`：家庭成员（年龄段、每人口味、个人忌口、可选品类偏好覆盖）
  - `ingredients`：常见 / 在售菜品（`cities[]`；`kind` 主料/调味；`availability` 四季/时令；`onConfirmPage`；来源、更新时间）
  - `ingredient_sync_jobs`：美团侧抓取任务状态（任务目标城市、日期、成功条数）
  - `recipes`：菜谱库（含 `dishForms` / `stapleForms` 品类标签、`cities[]`）
  - `meal_logs`：饮食记录（仅用户确认或主动记录后写入）
  - `recommendations`：推荐历史与反馈（含「换一批」）
  - `holidays`：按年打包的节日日历（`year` + `items`：日期、中英文名、稳定 id；供节日聚会推送）

**关键实现点**：
1. **默认菜列表**：按 `users.city` 读 `ingredients`。接口返回时令主列表 + 四季常见；进入页**只全选时令主列表**；四季常见默认计入已选但不铺开。无城市数据时回退全国项。长尾与调味不进主列表。
2. **菜品日更**：云函数定时任务，试点城市 = 省会 + 直辖市；写入 / 更新 `ingredients`（注意合规与风控：频率、字段最小化、失败重试与人工兜底库）。
3. **推荐引擎**：云函数纯规则引擎优先；输入 = 食材 ∩ 场景 ∩ **家庭忌口硬排除（菜谱食材 avoidTags ∩ 词表，不用菜名）** ∩ 成员忌口降权 ∩ 菜式品类加权 ∩ 近 7 日 `meal_logs`。成员忌口占比配额后续细化。非常规方案规则见详细设计「推荐与反馈」。
4. **人数 / 搭配预填与推荐**：
   - `mealType === 日常`：表单初始化写入 `defaultPeopleCount`、`defaultCombo`；用户修改后仅当确认采纳日常方案时可选写回。
   - 非日常：人数、搭配初始为空；监听人数变化，调用 `suggestComboByPeople(n)`（规则表，如 1→一荤一素，2→一荤一素一汤，≥4→两荤两素一汤）填入推荐搭配，用户可改；**禁止**写回默认搭配。
5. **菜式品类**：画像存 `prefer` / `neutral` / `avoid`；`prefer` 加分并可触发对应非常规方案，`avoid` 降权且不出该类非常规方案（未写入家庭忌口则不从家常池硬删）。菜谱入库必须带品类标签。
6. **饮食记录**：禁止在「采纳推荐」时自动写 `meal_logs`；写入入口为：进场确认弹层、手动、语音（拍照后置）。
7. **进场确认**：锚点 = 最近一次 `acceptedAt` 或 `engagedAt`（可见≥30s）取更晚者；无锚点不弹层。候选 = 锚点 plan 菜 − 「近期已记录」（`createdAt >=` 锚点时刻）。弹层**默认不勾选**，用户勾选后批量写 `meal_logs`。
8. **换一批 / 不行**：`swap` 仅当次排除已展示菜；`reject` 弹原因面板（可不选）并长期降权，与 swap 分记。
9. **购买食材页**：由方案菜谱聚合去重生成清单；菜谱字段区分 `mainIngredients` 与 `seasonings`，渲染时主料在前、调味在后。点「可以」→ `navigateTo` 食材页并标记 `accepted=true`；「查看购买清单」→ 同一页且 `accepted=false`。
10. **用餐时间**：用成员 / 家庭配置的午饭晚饭时刻，后续可做订阅消息提醒「记一下今天吃了什么」（提醒本身可放后期）。
11. **菜谱库**：先整理 100-200 道家常菜 JSON 入库；与多顿、几荤几素、菜式品类标签对齐；带 `cities[]`（空=全国）；须含火锅 / 面条 / 水饺样本；每道菜拆主料 / 调味便于清单排序。

### 六、最小可行版本（MVP）范围

第一版只做：
- 时令常见菜主列表 + 全选确认（有上限）；四季常见默认计入可取消；手动补菜 + **语音补菜**
- 当次场景：日常自动带出默认人数 / 搭配（可改）；非日常不预填人数，输入人数后推荐搭配，几顿默认 1 顿且不区分午晚；节日列表可先写死几个
- 微信登录 + 默认昵称「大厨xxxx」与默认头像（可在「我的」修改）；手机号选填
- 按人画像：年龄段、口味、个人忌口；家庭：家庭忌口（硬排除）、菜式品类偏好、默认人数、用餐时间、默认搭配
- 推荐：家庭忌口硬排除；成员忌口 MVP 先降权，占比配额后续细化；菜式品类按画像加权；可出火锅 / 面条 / 水饺非常规方案（至多一套）
- 进场确认近期是否吃过（默认不勾选；锚点为采纳或推荐页停留≥30s；无锚点不弹）
- 规则引擎推荐 + **换一批**
- 点「可以」自动进购买食材页（主料优先、调味靠后）；推荐页另有「查看购买清单」入口
- 手动 + **语音**记录饮食

**不做 / 可延后**：
- 成员忌口的完整占比配额与小样本取整策略（先降权）
- 美团菜品抓取日更（可先用静态城市菜列表；接口与表结构先预留）
- **线上商超接入推荐**（见「八、未来需求点」；MVP 仅线下菜场 / 静态列表）
- 拍照识别食材、拍照记饮食（入口不展示，实装后再放出）
- AI 生成菜谱
- 社区、分享、排行榜
- 用餐时间订阅消息推送

### 七、验证指标

- 用户是否在菜场完成「确认食材 + 场景」并看到推荐
- 「进场确认吃过」的完成率与勾选比例（勾选数 / 候选数）
- 用户是否主动完成饮食记录（手动 / 语音）
- 「换一批」点击率与采纳前平均换批次数
- 点「可以」后进入食材页的比例；从未采纳入口查看清单的比例
- 7 天内回访率
- 日常默认搭配被复用的比例

> 可执行测试用例见 [`doc/测试用例.xmind`](./测试用例.xmind)（XMind）。

### 八、未来需求点

#### 8.1 线上商超接入推荐

**诉求**：除线下菜场「确认今天有什么」外，用户也可**接入线上商超**，用商超在售 / 可加购 SKU 作为「今天可选食材」来源，再走同一套画像与推荐引擎，尤其适合 **盒马** 等 SKU 特别丰富的商超（品类细、预制与生鲜并存，比传统菜场列表更能撑起多样化搭配）。

**示意能力**：
- 用户选择渠道：线下菜场（现状） / 指定线上商超（如盒马，后续可扩美团买菜、叮咚等）。
- 拉取或同步该商超当前可售 SKU（需官方合作或合规接口；按门店 / 配送范围过滤）。
- 推荐与清单基于商超 SKU 生成；购买食材页可导向商超加购 / 下单（与盈利方案中的分佣候选衔接，仍非 MVP）。
- 与现有流程兼容：进场确认、忌口、搭配、多顿、换一批逻辑复用；仅「可选食材」数据源切换。

**为何后置**：依赖商超开放能力与门店库存实时性；SKU 映射到菜谱主料需要品类对齐；合规与商务周期长。当前以线下菜场 + 静态 / 日更常见菜列表验证推荐闭环即可。
