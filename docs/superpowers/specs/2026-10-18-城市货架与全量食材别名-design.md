# 城市货架与全量食材别名

状态：已定稿  
日期：2026-10-18

## 目标

用美团菜场采集数据构建：

1. **分城市、分类别**的食材货架（某城有的，别城未必有）
2. **全量食材**（合并所有城市 + 现有 builtin，只按类别）
3. **通用名 ↔ 别名**映射，供写菜谱与推荐匹配
4. 推荐时：用**该城货架**（经别名一次展开）去筛**全量菜谱**

人工审核只关心两件事：太长名怎么拆；哪些不要 / 哪些可收。

## 已定决策

| 项 | 决定 |
|----|------|
| 城市货架用名 | **保留菜场当地名**（如鸡脚），不入库时强行改成通用名 |
| 菜谱用料名 | 菜名里已出现的食材用菜谱叫法；否则用通用名 |
| 分类 | 先用美团类（素菜 / 荤菜 / 海鲜水产 / 火锅食材 / 豆制品 等）；日后映射 App 分类 |
| 全量来源 | **菜场清洗结果 ∪ `ingredients-builtin`**，按类去重 |
| 匹配性能 | 货架**一次**别名展开 → 集合包含（或倒排）；禁止「每个别名搜一遍菜谱」 |
| 词典角色 | 分词词典从全量/货架**派生**，不当人工主维护物 |

## 数据产物

建议落在 `data/catalog/`（路径可在实现计划里微调）：

### 1. 城市货架 `cities/{城}/ingredients.json`

```json
{
  "city": "重庆",
  "categories": {
    "荤菜": ["鸡脚", "牛百叶"],
    "素菜": ["折耳根"]
  },
  "_meta": { "source": "meituan-clean", "updatedAt": "..." }
}
```

- 名称为清洗后的**当地叫法**，不去别名归一。
- 由 `screenshots_inbox/{城}/ingredients-cleaned.json`（或等价清洗产物）导出/同步。

### 2. 全量食材 `ingredients-all.json`

```json
{
  "categories": {
    "荤菜": ["鸡爪", "鸡脚", "牛百叶", "..."],
    "素菜": ["折耳根", "菠菜", "..."]
  },
  "_meta": {
    "sources": ["cities/*", "ingredients-builtin.jsonl"],
    "note": "按类合并去重；同一字符串可出现在多类（暂不强制一类一物）"
  }
}
```

- 只按类、不按城。
- builtin 的 App 类（如 `meat`）在合并脚本里映射到美团类，或先挂「未映射」桶，实现计划里定一张粗映射表。

### 3. 别名表 `aliases.json`

```json
{
  "鸡爪": ["鸡脚", "凤爪"],
  "番茄": ["西红柿"]
}
```

- 键 = **通用名**；值 = 别名列表（不含通用名自身亦可，匹配时自动把键算进等价集）。
- 脚本生成反向索引：`鸡脚 → 鸡爪`，供展开与归一。

### 4. 人工清单（审核入口）

| 文件 | 用途 |
|------|------|
| `review/reject.txt` | 不要的名（整行拒收；可被清洗规则吸收） |
| `review/accept.txt` | 可收但被规则误杀的名（白名单） |
| `review/segment-hints.txt` | 太长粘连怎么拆，如 `洋葱炒猪肝=洋葱+猪肝` |

清洗 / 合并流水线读这三份；**不要求**人先编完整词典。

## 流水线

```text
菜场采集 (OCR / Appium)
  → 规则清洗 (广告/乱码/非生鲜丢弃；虾滑/牛肉丸等例外)
  → 应用 reject / accept / segment-hints
  → 写出 城市货架
  → 合并 城市货架 ∪ builtin → 全量食材
  →（可选）由全量生成分词词典，供下次粘连拆分
```

现有 `tools/meituan-automator/clean_city_products.py` 继续做规则清洗；新增「导出城货架 + 合并全量 + 读审核清单」步骤（脚本名实现时定）。

## 菜谱与推荐

### 写菜谱

- 用料字符串：优先菜名内已出现的叫法；否则用 `aliases.json` 的通用名。
- 生成菜谱时可用的词表 = 全量名 ∪ 所有别名（便于覆盖口语）。

### 推荐（按城）

1. 取该城货架名集合 `S`。
2. 对每个 `x ∈ S`，若 `x` 是某通用名或其别名，则把该通用名及其全部别名并入 `S'`（**一次展开**）。
3. 菜谱可推 ⟺ 该菜用料集合 ⊆ `S'`（调味是否计入另循主数据设计；本设计不改）。

示例：重庆有「鸡脚」→ `S'` 含 鸡脚/鸡爪/凤爪 → 《红烧鸡爪》可命中。

## 人工审核工作流

1. 跑清洗 + 合并后，产出「待审」摘要（过长名、低频名、仅单城出现等——实现时可分期）。
2. 人只改三份清单：
   - **太长** → 写入 `segment-hints`
   - **不要** → `reject`
   - **误杀可收** → `accept`
3. 重跑清洗/合并；别名表可逐步手补或从「同城多叫法」半自动建议（后置）。

## 与现有文档关系

- 城市决定当地常见食材、推荐用货架筛菜谱：与 `doc/需求概述.md`、家庭菜系偏好设计一致。
- 菜场规模档截断：仍见 `2026-10-14-菜场规模与食材列表档位-design.md`（后置）；本设计只定名单与别名结构。
- 同方案去重曾注明 MVP 不做完整别名：本设计**开始建立**别名表，供匹配用。

## 非目标（本设计不做）

- App 确认页分类映射与 UI
- 别名自动发现的完整算法（可后置半自动建议）
- 云函数日更与合规抓取策略（已有需求概述）
- 改推荐云函数实现细节（仅约定匹配语义）

## 成功标准

- 能按城打开「该类有哪些当地食材」
- 能打开「全国按类全量」且含 builtin ∪ 各城
- 鸡脚/鸡爪经别名能互相命中菜谱，且匹配为 O(货架展开 + 遍历/倒排)，非按别名反复搜库
- 新人接手时：维护 reject/accept/segment-hints 与 aliases，而不是从零编分词词典
