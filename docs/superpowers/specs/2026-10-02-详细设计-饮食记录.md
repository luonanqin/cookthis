## 1. 范围

- `meal_logs` 写入：手动、语音、进场确认；拍照后置且入口不展示  
- 进场确认弹层：候选组装、去重、确认落库  
- **硬规则**：采纳推荐 **不** 写 `meal_logs`

---

## 2. 数据模型 `meal_logs`

| 字段 | 说明 |
|------|------|
| `uid` | — |
| `logId` | — |
| `date` | 业务日 `YYYY-MM-DD`（用户本地时区） |
| `meal` | `lunch` \| `dinner` \| `other` \| `unknown` |
| `dishNames` | string[] |
| `ingredientNames` | string[] 可选，供推荐新鲜度降权（主料重叠） |
| `source` | `manual` \| `photo` \| `voice` \| `confirm` \| `plan_ate` |
| `recommendationId` | 可选，关联推荐会话 |
| `requestId` | 可选 |
| `createdAt` | 服务器时间，**用于「近期已记录」窗口** |

### 2.1 完整示例（1 用户 : N 记录；可选关联 1 次推荐）

关系：同一 `uid` 多条 `meal_logs`；一条记录可含多道菜名；可选挂 `recommendationId` / `requestId`。

```jsonc
[
  {
    "uid": "u_demo001",                        // 用户
    "logId": "log_001",                        // 记录 id
    "date": "2026-10-02",                      // 业务日
    "meal": "dinner",                          // 餐次：晚饭
    "dishNames": ["红烧茄子", "紫菜蛋花汤"],     // 吃过的菜名（可多道）
    "ingredientNames": ["茄子", "鸡蛋", "紫菜"], // 相关主食材（新鲜度降权用）
    "source": "manual",                        // 来源：手动记录
    "recommendationId": null,                  // 未关联推荐文档
    "requestId": null,                         // 未关联推荐请求
    "createdAt": "2026-10-02T19:30:00.000Z"    // 写入时间（去重窗口用）
  },
  {
    "uid": "u_demo001",
    "logId": "log_002",
    "date": "2026-10-03",
    "meal": "dinner",
    "dishNames": ["土豆烧肉", "蒜蓉青菜", "蛋花汤"],
    "ingredientNames": ["猪肉", "土豆", "青菜", "鸡蛋"],
    "source": "confirm",                       // 来源：进场确认
    "recommendationId": "rec_doc_001",         // 关联推荐会话文档
    "requestId": "req_20261003_001",           // 关联推荐请求 id
    "createdAt": "2026-10-04T09:00:00.000Z"
  }
]
```

读法：进场确认一次可写入多道菜；`requestId` 与推荐会话对齐，便于「采纳之后已记录」去重。

## 3. 进场确认

### 3.1 触发

首页点击「今天菜场有什么」→ `meals.confirmCandidates`。

### 3.2 候选组装

1. 在该 uid 近期 `recommendations`（近 **7** 天，与推荐「刚吃过」窗口一致）中找 **唯一最新锚点**：  
   （超过 7 天仍未进场确认的采纳/停留视为已过期，不再弹。）  
   - 候选范围：有 `acceptedAt`（点过「去买菜」）或有 `engagedAt`（推荐页可见 ≥ **30 秒**）的会话  
   - 取 **锚点时刻最晚** 的那一条；锚点时刻 = `max(acceptedAt, engagedAt)`（该条上有哪个用哪个）  
   - **不往前翻**：不因最新条已处理 / 候选空而去用更早的会话  
2. **没有锚点**（从未采纳且从未有效停留）→ **不弹层**，直接进输入页  
3. 若最新锚点已 `entryConfirmHandled === true`（曾确认或跳过）→ **不弹层**  
4. 菜名来源：该锚点会话对应 plan 的菜  
   - 若锚点靠采纳：用 `acceptedPlanIndex`  
   - 若锚点靠停留：用 `engagedPlanIndex`  
   - 若同条既采纳又停留且时刻相同：优先 `acceptedPlanIndex`  
5. **近期已记录** = `meal_logs` 中 `createdAt >=` 锚点时刻 的所有 `dishNames`（含进场确认、手动/语音，以及已选方案里点选产生的 **`source=plan_ate`**）  
6. 候选 = 锚点 plan 菜名 − 近期已记录（菜名去空白归一化）；**已标记过的菜不出现在弹层里**  
7. 若候选为空（例如该方案菜已在「已选方案」里全部点选已吃）→ **不弹层**，直接进输入页  

### 3.3 弹层交互

- **默认全部不选**，只展示候选菜名；由用户勾选吃过的  
- 可提供「全选」快捷，但不预勾  
- **确认提交** → `meals.confirmWrite`：仅对**勾选**项写 `meal_logs`（`source=confirm`，`date=今天`）；无论勾选 0 道还是多道，均视为**已处理本锚点**  
- **跳过** → 不写菜，直接进输入页（打 `confirm_sheet_skip`）；同样视为**已处理本锚点**  
- **已处理**：在锚点对应的 `recommendations` 上写 `entryConfirmHandled=true`、`entryConfirmHandledAt=now`（确认与跳过都写）。下次进菜场仍先取「最新锚点」；若仍是该条且已处理 → **不弹**，也**不会**改用更早的会话。  
- 仅当之后又产生**更新的**采纳 / 有效停留（锚点时刻更晚，且尚未处理）时，才可能再次弹层。  

### 3.4 「近期已记录」口径

窗口起点 = **当前选用的最新锚点**时刻，不是「最近 7 天」日历窗（7 天窗留给推荐：同菜名硬排除 + 主料重叠降权）。

## 4. 手动记录

`meals.addManual`：

- 入参：`dishNames[]`，可选 `date`/`meal`，可选从历史推荐多选  
- `source=manual`  
- 埋点 `meal_log_manual`

### 4.1 语音记录

`meals.addVoice`（或先转写再走与手动相同的确认提交）：

- 录音 → 转写 → 抽出菜名，用户确认后写入，`source=voice`  
- 埋点 `meal_log_voice_start` / `meal_log_voice_result`

拍照记录：**不展示**入口；预留 `source=photo` / `addPhoto` / `meal_log_photo_*` 命名，实装后再露出。

### 4.2 删除已吃记录

用户可在历史 / 记录列表中**按条删除**自己的 `meal_logs`（误记、记错菜时纠正），删除后不再参与近 7 日硬排除与新鲜度。

- **接口**：`meals.remove`（或 `delete`）：入参 `logId`；仅允许删除 `uid` 匹配当前用户的文档；成功则物理删除（MVP 不做软删回收站）。
- **UI**：记录列表每条提供删除入口（如右滑删除或行内删除）；二次确认文案简短（如「删掉这条已吃记录？」）。
- **埋点**：`meal_log_delete`（带 `logId` / `source` 可选）。
- **与进场确认**：删除后，若同一锚点仍未 `entryConfirmHandled` 且菜名重新落入「未记录」，下次进场确认候选可再次出现该菜；若锚点已处理则仍不弹层（收口规则不变）。

### 4.3 已选方案内点选已吃（即时）

入口与列表见推荐与反馈 **§3.3.1**。本节目的：从已采纳方案按**道**标记/取消已吃，操作尽量少。

**交互**

- 菜前勾选，**视觉与进场确认一致**（勾 + 选中变色）。  
- **无单独「提交」**：点选 = 立刻记为已吃；再点 = 立刻取消已吃。  
- 列表顶长期小字：「点选标记已吃，再点取消」；首次进页另出悬浮气泡（只一次）。  
- UI 可乐观更新；失败则回滚勾选并 toast。

**写入模型（一道菜一条日志）**

- 点选：`meals.planAteOn`（名称可调整）写入一条 `meal_logs`：  
  - `dishNames: [该菜名]`（单元素）  
  - `source: plan_ate`  
  - `recommendationId` / `requestId` 必填  
  - `date` 默认今天；`ingredientNames` 按菜谱解析（与 confirm 相同思路）  
- 取消：按该条 `logId` 调用 `meals.remove`；或 `meals.planAteOff`（`requestId` + 归一化菜名）服务端查到唯一 `plan_ate` 日志后删除。  
- **幂等**：同一 `uid` + `requestId` + 菜名已存在 `plan_ate` 时，再 On 不重复插入；Off 时无记录视为成功。  
- 进场确认的 `confirmWrite` 仍可为「一次多菜一条日志」；与 `plan_ate` 并存时，去重一律按**菜名**集合，不要求日志条数形态一致。

**埋点**：`plan_ate_toggle`（`on`/`off`）。

## 5. 供推荐消费

`recommend` 读取近 **7 天**（可配置）`meal_logs`：

- **硬排除**：相同 `dishNames`（或可关联到同 `recipeId`）  
- **软惩罚（新鲜度）**：候选 `mainIngredients` 与近期 `ingredientNames` 重叠 → 按 **主料分档 + 时间衰减** 加分，**分越高越靠后**，不硬删；公式与例子见推荐与反馈详细设计 **§3.0.4**。调味不参与。  

与进场确认窗口（锚点时刻之后）是两套逻辑，勿混用。

## 6. 云函数

| 方法 | 说明 |
|------|------|
| `confirmCandidates` | 返回候选列表（只评估最新锚点；已 `entryConfirmHandled` 则不弹） |
| `confirmWrite` | 批量写 confirm 日志，并将锚点会话标为 `entryConfirmHandled` |
| `confirmSkip` | （可与写空合并）仅将锚点标为 `entryConfirmHandled`，不写菜 |
| `addManual` | 手动记 |
| `addVoice` | 语音记（转写后确认写入） |
| `list` | 「记一下」近期记录分页：默认每页 **10** 条（`limit`）；`cursor={ createdAt, logId }` 拉下一页；返回 `items` + `nextCursor`（无更多则为 `null`） |
| `remove` | 按 `logId` 删除当前用户的一条已吃记录 |
| `planAteOn` / `planAteOff` | 已选方案内点选/取消已吃（§4.3） |

## 8. 边界

采纳 / 有效停留只改 `recommendations` → 推荐与反馈。候选菜名来自锚点 plan，依赖 `plans` / `acceptedPlanIndex` / `engagedPlanIndex`。进场确认的「处理过」标记 `entryConfirmHandled` 也写在同一条 `recommendations` 上。
