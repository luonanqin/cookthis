# 做饭能力与菜品难度匹配

日期：2026-11-05  
状态：已实现  
实现计划：[`../plans/2026-11-05-做饭能力与菜品难度.md`](../plans/2026-11-05-做饭能力与菜品难度.md)  
概述：`doc/需求概述.md` §8.7  

## 背景

用户做饭能力差很大；把步骤多、火候难的菜推给不太会做的人，体验差。现有「做饭时间预算」与菜谱 `minutes` 只近似耗时，**不等于**难度。

## 决策摘要

| 项 | 决定 |
|----|------|
| 能力来源 | 引导内**选题测验**定档（自报三档 chip **不做**）；行为校准后置 |
| 勾选含义 | 做过，**或**没做过但觉得简单、做得了（A+C 合成一句文案） |
| 测验形态 | 三组各 8 道：易 / 家常 / 进阶；组标题可弱化或不标「难度」字样 |
| 定档规则 | 从高到低看勾选数（规则 A）；每组阈值 **超过 4 道（≥5）** |
| 挂载 | 账号本人 `users.cookSkill`；不按成员选「谁做饭」 |
| 未填 / 跳过 | 推荐按 **home（家常）**；不硬排 advanced |
| 菜谱 | `difficulty`: `easy` \| `home` \| `advanced`；缺省用 `minutes`+启发式 |
| 推荐 | 差一档软降权；差两档硬排除（新手 × advanced） |
| 「我的」 | 城市与菜系之间内嵌探针（可回填）；保存须 ≥1 道（引导仍可跳过）；无档位结论文案入口 |

## 1. 引导测验 UI

插在完整引导步骤中：**所在城市之后、菜系偏好之前**（与其他设置同风格，**可跳过**，不单独强调「可选」）。

```
标题：做饭水平（与「我的」同款）
副文：选择会做或者没做过但觉得简单的

[ 轻松上手 ]     （内部 = easy，文案可不暴露 difficulty）
  ☐ 菜1 … ☐ 菜5

[ 家常水平 ]
  ☐ …

[ 进阶一点 ]
  ☐ …

[ 下一步 / 跳过 ]
```

- 预置 **24** 道稳定示例菜（非每次随机），须带明确 `difficulty`，名面熟、少地域偏门。  
- 「下一步」须至少勾 1 道；零勾选拦住并标题闪红（见 [`2026-11-06-引导下一步校验-design.md`](./2026-11-06-引导下一步校验-design.md)）。  
- 跳过 = 清除 `cookSkill` / 探针勾选（视同 home；避免旧勾选回填）。  
- 埋点：`onboarding_cook_skill_step`；提交时带各组勾选数与结果档。

## 2. 定档算法

```
nE, nH, nA = 易/家常/进阶勾选数（0～8）；「下一步」时 nE+nH+nA >= 1
若 nA >= 5 → skilled      // 超过 4 道
否则若 nH >= 5 → home
否则 → beginner          // 含几乎只勾了易（至少 1 道）
若整步「跳过」→ 清除档位与勾选（推荐当 home；与点「下一步」写入不同）
```

「我的 → 重新测做饭水平」：同 UI、同算法，覆盖 `cookSkill`。重测若选跳过/取消，**不**清空已有 `cookSkill`。

落库：`cookSkillProbeAt`、`cookSkillProbeCounts: { easy, home, advanced }`、`cookSkillProbeDishIds: string[]`（回填勾选）。详见 [`2026-11-06-我的偏好做饭水平内嵌-design.md`](./2026-11-06-我的偏好做饭水平内嵌-design.md)。

## 3. 字段

### 用户

```ts
cookSkill?: "beginner" | "home" | "skilled"
// 缺省 / 未写 → 推荐逻辑当 "home"
```

### 菜谱

```ts
difficulty?: "easy" | "home" | "advanced"
```

缺省推断（阈值实现时可调，须单测固定；复杂形态以 catalog 已有 `dishForms` 为准，如蒸、烤、火锅等）：

- `minutes <= 20` 且无复杂形态 → `easy`  
- `minutes >= 50` **或**含复杂形态 → `advanced`  
- 其余 → `home`  

有显式 `difficulty` 时**不**用推断覆盖。本地 catalog 可用 `scripts/backfill-recipe-difficulty.js --apply-probe-names --apply-inferred` 把空白写成与运行时一致的档位，便于维护时扫一眼；之后人工改某一档不会被脚本覆盖。

## 4. 推荐匹配

在现有家常候选管线中，解析菜谱有效难度 `d`，用户有效能力 `s`（缺省 home）：

| s \ d | easy | home | advanced |
|-------|------|------|----------|
| beginner | 通过 | 软降权 | **硬排除** |
| home | 通过 | 通过 | 软降权 |
| skilled | 通过 | 通过 | 通过 |

- **硬排除**：新手拉取菜谱池时 `where.difficulty ∈ {easy,home}`（与 `recipeDifficultyInFilter` 一致）；内存候选阶段仍做一遍兜底。  
- **软降权**：并入 `softPenalty`（分值实现时定，须低于家庭忌口硬排、可与口味软分同量级）。  
- 会做用户不对 easy 额外加权（避免全是白开水菜）；仅保证 advanced 不被挡。  
- home / skilled / 未填：拉库不加 difficulty 条件（未填当 home，advanced 只软降不硬排）。

### 4.1 云库索引（集合 `recipes`）

新手拉池查询形态（`recommend` → `loadRecipeBatch` → `recipeListWhere`）：

| 场景 | `where` |
|------|---------|
| 有城市 + beginner | `{ cities: '<城名>', difficulty: _.in(['easy','home']) }` |
| 全国补池 + beginner | `{ cities: [], difficulty: _.in(['easy','home']) }` |
| 非 beginner | 仅 `{ cities: … }`（与改前相同，不加 `difficulty`） |

**控制台建索引（全部普通索引，不要勾唯一）：**

| 索引名（建议） | 字段 | 排序 | 用途 |
|----------------|------|------|------|
| `cities_difficulty` | `cities`、`difficulty` | 均为升序 | beginner 组合查询；缺则易报「建议创建索引」或扫全表慢 |

说明：

- 文档须先带齐 `difficulty`（导入含该字段的 `recipes-for-import.json`），否则 `_.in(['easy','home'])` 匹配不到未写字段的行。  
- 仅建 `difficulty` 单字段通常不够（查询同时等值匹配 `cities`）。  
- 控制台也可在云函数报错弹窗里点「去创建」按提示生成；与上表字段一致即可。  
- 内存硬排仍保留：漏导字段或脏数据时不当洞。

空结果：与现有「食材不够」同路径；若因难度硬排导致过空，可在实现时对 beginner 放宽「家常软降不硬排」——**本期不自动放宽 advanced 硬排**。

## 5. 与现有能力的关系

- **做饭时间预算** / `minutes`：继续管耗时偏好；与难度正交（短但难的菜仍可能 advanced）。  
- **菜式品类 prefer**：不变；难度在品类过滤之后或并行软硬规则中施加。  
- **行为校准**（换一批、不行等反推能力）：明确后置。

## 6. 非目标

- 向用户展示「系统判断你是新手」等结论文案（可只在测完给中性「已根据选择优化推荐」）  
- 成员级做饭能力、聚会按某人能力  
- 用选题结果当「想吃清单」写入已选食材  
- 本期行为推断改档  

## 7. 成功标准

- 引导可完成 15 选并写出 `cookSkill`；跳过则推荐不因难度硬排 advanced。  
- 新手测完后，方案中不出现预标 `advanced` 的菜；家常档仍可能出现但更少。  
- 无 `difficulty` 的菜走兜底推断，推荐不崩溃。  
- 「我的」重测可改档并影响下一次 `create`。
