## 1. 范围

- 确认页：时令主列表默认全选（有上限）；四季常见默认计入但不占主列表；调味不出现  
- 当次场景：饭菜类型（日常/聚会）、人数、搭配、忌口（聚会）、想做几顿；节日选择延后  
- 输出：`ingredientIds[]` + `scene` → 交给推荐  
- **不含**：美团抓取实装、拍照识菜（入口**不展示**；事件名可预留）

## 2. 食材列表

### 2.1 拉取 `ingredients.list`

入参：`city?`（缺省用 `users.city`）  

逻辑：

1. 查 `ingredients`：`cities` 为空（全国）或包含入参城市  
2. 若该城专属条数过少 → **fallback** 仅全国项，返回标记 `fallback: "national"`  
3. 分层返回（字段见主数据 §2.2）：

```ts
{
  seasonal: Ingredient[],     // onConfirmPage 的时令主料，已按类截断
  yearRound: Ingredient[],    // 四季常见主料
  fallback?: "national"
}
```

分类：`leaf` 叶菜 · `root` 根茎 · `fruit_veg` 茄果 · `bean` 豆类 · `mushroom` 菌菇 · `meat` 肉类 · `seafood` 水产 · `egg_dairy` 蛋奶 · `tofu` 豆制品  

`kind=seasoning` **不返回**（或单独忽略），不进确认页、不进已选主料。

时令主列表上限：每类约 6～10、合计约 40～70，按 `sort` 截。长尾不在 `seasonal` 里。

### 2.2 前端交互

- **主列表**：只渲染 `seasonal`，分类可折叠，进入时**默认全选**这些时令项  
- 全选 / 清空：只作用于主列表，不动四季常见  
- **四季常见**：默认全部计入已选；主列表不铺开。一条折叠摘要「四季常见 · 已计入 N 样」，点开可取消今天没有的。若家庭忌口含某大类（如 `pork`），对应食材**默认不计入**（仍可在折叠区看到并手动勾回，但不推荐这样做宗教忌口）  
- **自定义补菜**：用户输入名称 → 本地临时 id（`custom_xxx`）或调用 `ingredients.addCustom`（可仅本地）  
- **语音补菜**：**不展示**入口（与拍照同属后置）；上线后再做。事件名预留 `ingredient_voice_start` / `ingredient_voice_result`，入口未展示前不打  
- **拍照识菜**：**不展示**入口；上线后再做。事件名可预留 `ingredient_photo_*`，当前不打、不提示「暂未开放」

### 2.3 确认输出

`selected` = 主列表勾选 ∪ 未取消的四季常见 ∪ 手补。**必须含**未展开取消的四季项，否则家常菜会因缺鸡蛋/猪肉而配不出。

```ts
{
  selected: [{ id, name, category?, custom?: boolean, source?: "seasonal"|"year_round"|"manual" }],
  methodsUsed: ("default_list"|"manual"|"photo"|"voice")[]
}
```

埋点见埋点详细设计：`ingredient_*`、`ingredient_confirm`。

## 3. 当次场景 `scene`

```ts
{
  mealType: "daily" | "family_party" | "friends_party" | "holiday_party",
  holidayId?: string,          // mealType=holiday_party；对应 holidays.items[].id
  holidayDate?: string,        // 选中的该年公历 YYYY-MM-DD（快照，避免跨年歧义）
  peopleCount: number | null,  // 日常 = 档案+访客；非日常 = partyCounts 三档之和
  /** 日常：档案大/小/老（由 members 映射） */
  householdCounts?: { adult: number, child: number, elder: number },
  /** 日常：当次临时访客（不落库）；默认偏好见 §3.1.1 */
  guestCounts?: { adult: number, child: number, elder: number },
  /** 非日常：本场大/小/老（不预填、不落库）；默认偏好同 §3.1.1 访客表，见 §3.1.2 */
  partyCounts?: { adult: number, child: number, elder: number },
  combo: { meat, veg, soup } | null,
  partyAvoids?: string[],      // 仅非日常；当次硬排除（功能不变）
  mealSlots: MealSlot[],       // 想做几顿
  persistComboToDefault?: boolean  // 日常写回时只写 combo，禁止把访客写入 members
}

type MealSlot = {
  meal: "lunch" | "dinner" | "other",  // 保留午/晚；非日常用 other
  label?: string                       // 展示用，如「晚饭①」；不表示日历日
}
```

不设 `dayOffset`：推荐只按顿数出几套菜，**哪一天吃由用户自己安排**。

### 3.0 完整示例（当次：多食材 + 一 scene）

关系：一次提交 = **多条选中食材** + **一份 scene**（含多顿 `mealSlots`）。交给推荐后写入 `recommendations`。

读法：提交里含主列表时令菜 + 未取消的四季常见 + 手补；推荐与清单都认这一份 `selected`。各顿共用同一个 `combo`。

### 3.1 日常 vs 聚会

产品入口二选一：**日常** / **聚会**（原「非日常 / 请客」收口；实现上 `mealType !== 'daily'` 一律走聚会逻辑，历史枚举 `family_party` / `friends_party` / `holiday_party` 可保留但不分叉出菜）。

| | 日常 `daily` | 聚会（非 daily） |
|--|--------------|------------------|
| 人数 | 展示 `N人 · x大 y小 z老`（来自 members）；可按**档**步进加减，见 §3.1.1 | 三档大/小/老（初始 0，不预填档案）；见 §3.1.2；`peopleCount = 三档之和`（须 ≥1） |
| 搭配 | 预填 `defaultCombo`，**用户可改**荤素汤 | **不露出**荤素汤选择；`combo` 由 §3.2.1 `suggestPartyCombo` 自动生成并写入 scene |
| 几顿 | 快捷芯片 + **自定义弹窗**（午/晚步进），**区分午/晚**；见 §3.4 | **默认 1 顿**，可改顿数；**不区分午/晚**（`meal: "other"`） |
| 忌口 | 用画像，不在本页选 | 本页选 **`partyAvoids`（本场忌口，当次硬排除）**，不写回画像 |
| 写回默认 | 可写回 **combo**；禁止访客入 `members` | **禁止**写回（含 `partyCounts` / `combo` / 忌口） |

### 3.1.1 日常大/小/老与本次访客

**档案基准**（打开确认页时从 `members` 计算）：

- `child` = `ageBand === '5_15'` 人数  
- `elder` = `ageBand === '60_plus'` 人数  
- `adult` = 其余合法年龄段人数  
- 展示：`共 N 人 · {adult}大 {child}小 {elder}老`；`peopleCount` 初值 = N。

**交互（求简单）**：三档「＋ / −」，不是只拨一个总人数。

| 操作 | 行为 |
|------|------|
| 某档 ＋ | `guestCounts[档]++`；该访客**不落库**；偏好用该档默认（下表） |
| 某档 − | 若该档 `guestCounts>0` 则减访客；否则允许把该档「有效用餐人数」减到低于档案（仅影响当次 `peopleCount` 与软分用的用餐人集合——实现可将「少来的档案成员」从当次快照末尾省略，**绝不 delete members**） |

**访客默认偏好**（按档，不是一律按「大」）：

| 档 | 默认 `ageBand` | 默认 `taste` | 默认 `avoids` |
|----|----------------|--------------|---------------|
| 大 | `26_40` | `normal` | `[]` |
| 小 | `5_15` | `light` | `[]` |
| 老 | `60_plus` | `light` | `[]` |

推荐侧把「档案成员 + 展开后的访客」合成当次用餐人列表再算忌口/口味/小老软分（见推荐 §3.0.8）。  
永久加人：文案链到「我的 → 添加家人」。

### 3.1.2 聚会：大/小/老与本场忌口

**人数**：三档步进；**不**预填档案。初始 `partyCounts = { adult:0, child:0, elder:0 }`；`peopleCount = adult+child+elder ≥ 1` 方可继续。

**偏好**：本场用餐人按档位默认展开（同 §3.1.1 表），不落库。小/老**只影响软分**（少辣/清淡），**不**单独改 combo 结构（结构见 §3.2.1）。

**本场忌口**：本页多选 `partyAvoids`，当次硬排除，不写回 `familyAvoids`。

**搭配 UI**：**不展示**荤素汤选择；提交前用 §3.2.1 写入 `scene.combo`。推荐卡可展示一句「按这桌人数自动配的桌」（只读）。

### 3.2 日常按人数推荐搭配 `suggestComboByPeople(n)`

仅用于**日常**（或推荐页补选）需要按总人数给一版可改搭配时；**聚会不用本函数**。

- **荤** `meat = max(1, ⌊n / 2⌋)`  
- **素 / 汤**：按下表（用户可改）

| 人数 n | 推荐 combo (meat-veg-soup) |
|--------|----------------------------|
| 1 | 1-1-0 |
| 2 | 1-1-1 |
| 3 | 1-2-1 |
| 4–5 | 2-2-1 |
| 6 | 3-2-1 |
| ≥7 | ⌊n/2⌋-3-1（如 7→3-3-1，8→4-3-1） |

### 3.2.1 聚会自动搭配 `suggestPartyCombo(partyCounts, sessionSeed)`

**输入**：`partyCounts`；`sessionSeed`（如 `requestId`，用于稳定「随机」）。  
**输出**：`{ meat, veg, soup }`，写入 `scene.combo`；**不写回**画像。  
**UI**：确认页不露出该结果的编辑控件。

设 `n = adult + child + elder`（`n ≥ 1`），`hasChild = child ≥ 1`。

1. **荤底**  
   `meat = max(1, ⌊n / 2⌋)`  
2. **无小孩时荤 +1**  
   若 `!hasChild`：`meat += 1`  
3. **总菜数**  
   - 有小孩：`total = n`（至少一人一道，不加码）  
   - 无小孩：`total = n + extra`，其中 `extra ∈ {1, 2}`，由 `hash(sessionSeed + ':partyExtra')` **稳定抽取**（同一次推荐会话不变；换一批可带新 seed 或同 requestId 则不变——MVP：**同 `requestId` 固定**）  
4. **汤**  
   `soup = n ≥ 2 ? 1 : 0`  
5. **素**  
   `veg = total - meat - soup`；若 `veg < 1`，则 `total` 递增直至 `veg ≥ 1`（保证至少一素）。

**举例**（无小孩时 extra 取 1 或 2 之一）：

| n | 小孩 | meat | total | soup | veg（示例） |
|---|------|------|-------|------|-------------|
| 2 | 无 | 2 | 3 或 4 | 1 | 0→抬到至少 1 素后 total 可能再 +1 |
| 4 | 无 | 3 | 5 或 6 | 1 | 1 或 2 |
| 6 | 无 | 4 | 7 或 8 | 1 | 2 或 3 |
| 4 | 有 | 2 | 4 | 1 | 1 |
| 6 | 有 | 3 | 6 | 1 | 2 |

家常引擎仍按该 `combo` 从荤/素/汤桶取菜；软分见推荐 §3.0.8。

### 3.3 节日（延后 · 暂时隐藏）

- **当前产品不展示**节日选择入口（确认页已隐藏）；`scene.holidayId` / `holidayDate` 固定不传。  
- 数据与 `holidays` 集合、过滤工具可保留，供后续「聚会下可选节日标签 / 节日出菜」再用。  
- 自定义节日名后置。

### 3.4 想做几顿

- **不绑定日历日**：只表示要出几顿菜、午还是晚；用户自行决定哪天吃哪顿。各顿共用当次一个 `combo`（见用户画像 §2.5）。  
- **日常**（详见 [`2026-10-11-日常几顿快捷与自定义-design.md`](./2026-10-11-日常几顿快捷与自定义-design.md)）：  
  - 芯片：`一顿晚饭` / `一顿午饭` / `1午+1晚` / **`自定义`**（无「两顿晚饭」；多晚走自定义）。  
  - 点自定义 → **下半屏居中独立卡片**选午饭 ×N、晚饭 ×M（加减按钮；各自 0～7，合计 ≤14；初值 0+0，不从快捷反推；再次打开用上次确认值）。  
  - 弹窗确认后芯片文案为 `n午+m晚`（缺一侧则只显示有的一侧；仍 0+0 则保持「自定义」）。  
  - `mealSlots`：先午饭 `午饭①…`，再晚饭 `晚饭①…`；若组合恰等于某预设，**仍保持自定义高亮**。  
  - 提交：至少 1 个 slot；自定义 0+0 时提示 **「请先选择吃几顿」**，不创建推荐。  
- **聚会**：默认 `[{ meal: "other", label: "本场" }]`（1 顿）。用户只调顿数（建议 ≤7），不选午饭/晚饭；多顿为 `other` + 序号 label。

## 4. 页面结构建议

同一「输入流程」内两段（可同页折叠或上下分区）：

1. 食材确认  
2. 场景设置  

进入本页之前：首页 → 进场确认弹层（见饮食记录详细设计）。

提交：校验食材非空、场景完整 →  
- 若日常且需轻量补全（见用户画像 §4.2）→ 先弹层，保存/跳过后再 `recommend.create`  
- 否则直接 `recommend.create`。  
- **`create` 凑不出任何方案（重要）**：**不**进入推荐页；留在本页弹出与推荐页**同一款**窄居中弹窗——仅标题「食材不够出菜了」，按钮「好吧」（浅底色）；关闭后用户可改食材/场景再试。细则见推荐详设 §3.1.1。
