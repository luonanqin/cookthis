## 1. 范围

- 规则引擎：`recommend.create` / `swap`  
- 反馈：`accept` / `reject`；换一批权重信号  
- 推荐页补选搭配  
- 购买食材清单按分类聚合、每行 2 个；底部菜谱弹层（按菜+食材）  
- **不含**：AI 生成菜谱、成员忌口占比配额（仅降权）

## 2. 数据模型 `recommendations`

| 字段 | 说明 |
|------|------|
| `uid` | — |
| `requestId` | 一次输入确认生成的会话 id |
| `scene` | 提交时 scene 快照 |
| `selectedIngredients` | 食材快照 |
| `plans` | Plan[] 当前展示的 1～3 套 |
| `excludedDishIds` | 换一批已排除的菜谱 id |
| `recipePoolIds` | 本会话已拉取的候选菜谱 id（分批累加） |
| `recipePoolExhausted` | 库侧已无更多可拉批次 |
| `swapCount` | 次数 |
| `feedback` | `{ type: "swap"\|"reject", reason?, planIndex?, at }[]`；swap 无长期降权，reject 有 |
| `accepted` | bool |
| `acceptedAt` | date? 采纳时间 |
| `acceptedPlanIndex` | number? 采纳的方案序号 |
| `engagedAt` | date? 推荐页累计可见首次达到 30s 的时刻 |
| `dwellMs` | number? 累计可见毫秒；可续增 |
| `engagedPlanIndex` | number? 达到 30s 时正在展示的 plan |
| `entryConfirmHandled` | bool? 进场确认弹层已处理（确认或跳过） |
| `entryConfirmHandledAt` | date? |
| `createdAt` / `updatedAt` | — |

### Plan 结构

```ts
{
  planIndex: number,
  planKind: "home" | "hotpot" | "noodle" | "dumpling",
  meals: [{
    slot: MealSlot,
    dishes: [{
      recipeId, name,
      meatVeg: "meat"|"veg"|"soup"|"staple"|"other",
      mainIngredients: string[],
      seasonings: string[]
    }]
  }],
  score?: number
}
```

`planKind`：`home` 家常荤素汤；`hotpot` 火锅；`noodle` 面条；`dumpling` 水饺。一套推荐里 **最多 1 个非 `home`**。

## 3. 引擎流水线

输入：`selectedIngredients`、`scene`、画像快照、近 7 日 meal_logs、`excludedDishIds`。

1. **候选池（分批）**：每次最多拉取 **50** 道菜谱——先 `cities` 含 `users.city` 的城内菜，不足再补 `cities: []` 全国菜；本会话已拉 id 记入 `recommendations.recipePoolIds`，换一批把当前菜并入 `excludedDishIds` 后若池耗尽或组不出方案，按同样规则再拉下一批 50（`recipePoolExhausted` 表示库侧已无更多）。组菜时仍要求主料 ⊆ 可选食材（允许缺少量调味及面食载体）；标签匹配。食材表可在云函数实例内缓存，不随每批菜谱重拉。  

2. **硬过滤**  
   - 家庭忌口或 `scene.partyAvoids`：用菜谱 **食材**（`mainIngredients` ∪ `seasonings` → `ingredients.avoidTags`）与忌口词表求交，有交集则丢弃；**不用菜名**判断（细则见用户画像 §2.3.1）  
   - 近 7 日吃过的**相同菜名**（或同 `recipeId`）：丢弃  
   - `excludedDishIds`：丢弃  

### 菜系偏好（家庭）

- 数据：`users.cuisinePrefs`；菜谱 `cuisineTags[]`（详见 2026-10-12 设计）。
- 硬排除：`cuisineTags ∩ avoid ≠ ∅` → 丢弃（家常与非常规均适用）。
- 软分：命中 `prefer` → `softPenalty` −20；无 tags 不加减。
- 顺序：忌口硬排除 → **菜系 avoid** → 软分（含菜系 prefer）。
- `home_style` 仅数据标签，不进用户词表。

3. **结构组合**  
   - **家常 `home`**：按 `scene.combo` 每顿凑齐 meat/veg/soup 数量  
   - 按 `mealSlots` 多顿排列，顿间尽量不重复 recipeId  
   - **非常规**：见 §3.6；与家常并列生成，**不**读 `scene` 上的品类勾选（场景无此字段）  
4. **打分**（加权求和 / 家常侧软惩罚，权重可配置常量）  
   - 食材覆盖度  
   - **口味 / 小老 / 成员忌口**：见 **§3.0.8**（日常含 `guestCounts`；非日常用 `partyCounts` 档位默认展开）  
   - 品类：家庭 prefer↑ avoid↓（无当次指定）  
   - **新鲜度**：见 **§3.0.4**（主料分档 + 时间衰减；降权不硬删）  
   - cookBudget vs recipe.minutes  
5. **组合多样性**（见 §3.0.5）：软排序之后、拼方案之前，用会话种子旋转桶内顺序，避免同默认输入每次都出同一批菜  
6. **输出** top 1～3 个 Plan（其中非 `home` 至多 1 套）；若家常也无法凑齐 → 返回 `emptyReason` / 埋点 `empty_recommend`（忌口过严/食材过少等）。非常规凑不出则只出家常，不算空结果。  
   **空结果交互（硬性，勿做成整页空态）**见 **§3.1.1**。

### 3.0 推荐页方案卡展示（食材信息）

**原则**：方案卡上要能略感采购负担，但**不能**摊开完整采购单，也不能另开「只看清单不采纳」入口——完整清单**只**经「去买菜」进入购买食材页。

| 区域 | 展示 | 不展示 |
|------|------|--------|
| 方案卡片 | 各顿菜名；**右下角一行**：`食材：猪肉、豆腐等2种`（每道菜取 1 个主料名去重拼接；优先未在已选中；仅 1 种时写 `食材：青菜`） | 菜名旁跟食材、完整清单、调味、「查看购买清单」、可勾选已买 |
| 购买食材页 | 按食材**分类**分组；每行 **2 个**食材可勾已买；无「已有 / 主料 / 调味」说明标签；**底部菜谱弹层**按菜+右侧食材（见 §4.4） | — |

- 可由客户端根据 `dishes[].mainIngredients` 与当次 `selected` 现算。

### 3.0.4 新鲜度软惩罚（主料分档 + 时间衰减）

**原则**

- 近 7 日 **相同菜名**（或同 `recipeId`）：**硬排除**（与本节无关）。  
- 主料与近期饮食记录重叠：**只加软惩罚、永不因新鲜度硬删**，避免土豆/青菜等大宗配菜把候选池掏空。  
- 家常桶内按软惩罚 **升序** 排列：**惩罚分越高越靠后**（不是「得分越高越好」）。  
- 调味（盐、酱油、蒜等）**不参与**新鲜度。  
- 名称暂做去空白归一；别名表（土豆/马铃薯）后续再加。

**软惩罚组成（可叠加）**

| 信号 | 惩罚分 | 说明 |
|------|--------|------|
| `reject` 长期降权 | **+100** | 点过「不行」的菜谱 |
| 成员/访客忌口命中 | **+40** | 不硬删；见 §3.0.8 |
| 小/老不适配（辣/重口） | **+15** | 当次用餐人含小或老且菜偏辣/重口；见 §3.0.8 |
| 口味不适配 | **+10** | 与多数用餐人口味冲突；见 §3.0.8 |
| 新鲜度 `freshPenalty` | **0～60** | 见下方公式，封顶 60 |
| （旧）主料重叠一律 ×10 | **废止** | 由分档公式替代 |

量级关系：口味/小老（约 10～15）＜ 刚吃过的主荤（约 24）＜ 成员忌口（40）＜ 明确拒绝（100）。

**主料档位（基础分）**

| 档位 | 基础分 | 示例 |
|------|--------|------|
| A 主荤 | **24** | 猪肉、牛肉、羊肉、鸡、鸭、鱼、虾等 |
| B 蛋豆主菜 | **12** | 鸡蛋、豆腐、豆干等 |
| C 大宗配菜 | **4** | 土豆、番茄、青椒、白菜、青菜、茄子等 |
| 未入表主料 | 按 **B（12）** | 默认 |

档位表可落在代码常量或主数据字段；MVP 可用常量名单，后续迁到 `ingredients` 元数据。

**时间衰减（近 7 日）**

对近期 `meal_logs` 中出现过的每个主料，按「距今天数」取系数；**同一食材只取最近一次**（不重复累加）：

| 距今 | 系数 |
|------|------|
| 0～1 天 | **1.0** |
| 2～3 天 | **0.6** |
| 4～6 天 | **0.3** |
| ≥7 天 | 不计入 |

**公式**

```
freshPenalty = min(60, Σ (档位基础分 × 该食材衰减系数))
```

候选总软惩罚 ≈ reject 项 + 成员忌口项 + `freshPenalty`（再与其他软项相加，若有）。

**例子**

*例 1 — 昨天吃了土豆烧肉（猪肉 A + 土豆 C）*

| 候选 | 重叠 | 计算 | freshPenalty | 直觉 |
|------|------|------|--------------|------|
| 青椒炒肉 | 猪肉 | 24×1.0 | **24** | 主荤刚吃，明显靠后 |
| 番茄炒蛋 | 无 | — | **0** | 优先 |
| 清炒土豆丝 | 土豆 | 4×1.0 | **4** | 配菜重复，几乎无感 |
| 土豆炖牛肉 | 土豆 | 4×1.0 | **4** | 换了肉种，只扣配菜 |
| 红烧牛肉 | 无 | — | **0** | 优先 |

*例 2 — 昨天番茄炒蛋 + 蒜蓉青菜（鸡蛋 B + 番茄 C + 青菜 C）*

| 候选 | 计算 | freshPenalty |
|------|------|--------------|
| 韭菜炒蛋 | 12×1.0 | **12** |
| 番茄牛肉 | 4×1.0 | **4** |
| 清炒青菜 | 4×1.0 | **4** |
| 青椒炒肉 | — | **0** |

*例 3 — 时间衰减：仅猪肉重叠的「青椒炒肉」*

| 距今 | 系数 | freshPenalty |
|------|------|--------------|
| 昨天（0～1） | 1.0 | **24** |
| 第 3 天（2～3） | 0.6 | **14.4**（实现可四舍五入为 14） |
| 第 5 天（4～6） | 0.3 | **7.2**（可取 7） |
| 第 8 天 | — | **0** |

*例 4 — 多主料与封顶：昨天火锅含羊肉 A + 牛肉 A + 小白菜 C*

- 候选只撞牛肉：`24×1.0 = 24`  
- 同时撞羊肉+牛肉+小白菜：`24+24+4 = 52`（未封顶）  
- 再叠更多 A 档时 **封顶 60**，避免超过 reject（100）的量级。

*例 5 — 与忌口 / 不行比量级（惩罚升序 = 越靠前）*

| 菜 | 新鲜度 | 其他 | 总惩罚 | 排序 |
|----|--------|------|--------|------|
| 番茄炒蛋 | 0 | — | **0** | 最前 |
| 青椒炒肉 | 昨天猪肉 24 | — | **24** | 次之 |
| 鱼香肉丝 | 0 | 成员忌口 +40 | **40** | 更后 |
| 红烧茄子 | 0 | reject +100 | **100** | 最后 |

*例 6 — 连续两天都买猪肉*

猪肉只取**最近一次**衰减（系数 1.0），不把两天猪肉分加两次。候选池若只剩猪肉菜，仍能凑方案，只是整桶惩罚偏高；**不会因新鲜度出不了菜**。

**验收要点**

- 刚吃过的主荤菜惩罚明显高于大宗配菜重复。  
- 隔 2～3 天、4～6 天惩罚递减；满 7 天窗口外为 0。  
- 同菜名 7 日内仍硬排除。  
- 单测可构造 meal_logs + 候选，断言 `freshPenalty` 与相对排序。

### 3.0.5 组合多样性（首次 `create` 也要变）

**问题**：当前家常拼装对桶内排序后用固定 `offset` 取菜，同食材 + 同场景 + 同近期记录时，**每次默认进推荐页都是同一批菜**；「换一批」才能换，体验像没随机组合。

**目标**：在仍尊重硬过滤与软排序的前提下，**每次新 `recommend.create`（新 `requestId`）** 展示的家常 / 非常规组合应有可感知差异；不要求用户先点「换一批」。

**MVP 做法**（实现落在 `buildHomePlans` / 非常规拼装；可单测）：

1. 桶内（meat / veg / soup 等）**先**按软惩罚升序（忌口命中、新鲜度、reject 降权等）。  
2. 再对每个桶做 **稳定旋转（或同分带内洗牌）**：  
   - 种子：`seed = hash(uid + requestId)`（**推荐用 requestId**，同一次请求可复现，不同次会话会变）  
   - 旋转量：`rotate = seed % bucket.length`（或对惩罚分相同/接近的子段分别旋转）  
3. 再用现有 offset 拼多套 plan；同一 `requestId` 内结果必须稳定（便于单测注入 seed）。  
4. **禁止**完全无视惩罚的纯 `Math.random`：高惩罚菜整体仍应靠后；只是「差不多好」的菜之间轮换。  
5. **非常规**（火锅 / 面 / 饺）：合格候选同样用同一会话 seed 轮换，避免总是同一锅底 / 同一涮品。  
6. **换一批 `swap`**：仍先并入 `excludedDishIds` 再重跑；重跑时继续用**当前** `requestId` 的 seed（或 `hash(requestId + swapCount)`，二选一写死并测稳）。排除当前菜是主手段，种子旋转是辅。

**验收**：

- 同默认食材 / 场景，连续两次完整进推荐页（两次 `create`）→ 方案菜名组合**不完全相同**（候选池够大时）。  
- 注入同一 `requestId` / seed → 输出完全一致。  
- 近期已吃同菜名仍硬排除；家庭忌口仍硬排除。  
- 「换一批」仍能换出与当前屏不同的菜。

### 3.0.6 多方案之间菜名重复上限

**问题**：同屏 1～3 套家常方案若只用桶内 `offset` 微调，常出现「方案 2 与方案 1 大半道菜相同」，对照挑选意义不大。

**范围**：同一次 `create` / `swap` 返回的多套 **`planKind: home` 方案**两两比较。非常规方案（火锅/面/饺）与家常之间不套用本上限（本就结构不同）。**不改变**过滤、软排序、会话种子旋转；同方案内去重见 **§3.0.7**（本上限在方案已拼成之后再约束方案间差异）。

**口径**：

| 单套菜道数（该 plan 全部 `dishes` 合计） | 与另一套 home 方案允许的相同菜上限 |
|------------------------------------------|--------------------------------------|
| **少于 5** | 相同菜名 / 同 `recipeId` **0 道**（不可相同） |
| **≥ 5 且少于 8** | 相同菜名 / 同 `recipeId` **最多 1 道** |
| **≥ 8** | 相同菜名 / 同 `recipeId` **最多 2 道** |

- **相同**：以 `recipeId` 为主；无 id 时用去空白归一化后的菜名。  
- **取向**：在能凑齐 `combo` 的前提下，**重复越少越好**（0 道重复优于顶格用满上限；少于 5 道时必须为 0）。  
- **两两都要满足**：方案 1 vs 2、1 vs 3、2 vs 3 均按上表；两套菜道数不一致时，**以两套中较大的那套菜道数**查表定上限（例：一套 10 道、一套 6 道 → 按 ≥8 处理，最多 2 道重复；一套 4 道、一套 3 道 → 按少于 5，不可有相同菜）。  
- **候选不足**：无法在上限内再拼出下一套差异化方案时，可少出一套（例如只出 1～2 套），**禁止**为硬凑 3 套而放开到「大半桌重复」；仍须保证至少有一套能展示（与空结果规则一致）。

**实现提示**（留给开发，本文不定死算法）：拼第 2、第 3 套时，将已收录方案的 `recipeId` 视作软/硬约束再跑 `fillMeals`；或拼完后若不满足上限则丢弃该套并加大 offset / 换种子重试。

**验收**：

- 小 combo（合计少于 5 道）同屏两套 home 方案，相同菜 = 0。  
- 中等 combo（合计 5～7 道）同屏两套相同菜 ≤ 1。  
- 家庭聚餐等大 combo（如 5 荤 4 素 1 汤 = 10 道）同屏两套 home 方案，相同菜 ≤ 2，且明显少于「几乎整桌一样」。  
- 候选极少时：允许只出 1 套，不出现空结果仅因本上限。

### 3.0.7 同一套方案内去重（菜名 / 近义 / 主料集合）

**问题**：

1. **同名不同 id**：菜谱库存在各地 city pack 同名菜（如多个「辣子鸡」），组方案若只按 `recipeId` 去重，同一套里会各挑一条，卡片上像同一道菜出现两次。  
2. **主料集合相同、菜名略异**：如「土豆烧牛肉」与「土豆炖牛肉」、「白菜炖豆腐」与「豆腐炖白菜」——主料集合相同（或仅顺序不同），同桌连出两道几乎无差别。  
3. **边选不记账 / 过早放宽**：同桶连取多道时若未同步更新已用菜名与主料签名，或不够数时放宽到「允许同名/同签名」，问题会在聚餐大 combo 下更明显。

**范围**：单套 **`planKind: home`** 在 `fillMeals` / `pickFromBucket` 过程中的约束。非常规方案（火锅涮菜等）本就允许多道不同涮品，**不**套用本节主料集合硬去重；同名涮品仍应避免重复 `recipeId`/菜名。与 **§3.0.6**（多方案之间）正交：先保证单套内部不「自撞」，再约束方案间重叠上限。

**过滤顺序**（推荐；由便宜到贵，硬→软）：

| 顺序 | 类型 | 规则 | 不够数时 |
|------|------|------|----------|
| 1 | 硬 | 本方案已用 **`recipeId`** | **不放宽** |
| 2 | 硬 | **归一化菜名**已出现（去空白；大小写不敏感若适用） | **不放宽** |
| 3 | 硬 | **主料集合签名**与本方案已选某道**完全相同**（见下） | **不放宽** |
| 4 | 硬 | **近义菜名**与本方案已选某道命中（见下） | **不放宽** |
| 5 | 软 | 尽量避开本方案**已用主料**（任一主料已出现则暂跳过） | **可放宽**（先放宽本步，再继续从桶中取） |

**主料集合签名（口径 A）**：

- 仅用菜谱 `mainIngredients`（名称归一化后排序拼接或排序后集合相等）；**调味不参与**。  
- **完全相同**才判撞车：`{土豆, 牛肉}` = `{牛肉, 土豆}` → 互斥；多一味（如再加青椒）→ **不**因此互斥。  
- 不采用「核心主料子集」或 Jaccard 阈值，避免误伤「土豆烧牛肉」与「青椒土豆丝」仅因共用土豆。

**近义菜名（兜底）**：

- 对菜名：去空白 → 去掉常见烹法词（至少含：烧、炖、炒、爆、焖、煮、蒸、拌、煎、烤、红烧）→ 剩余字符按序比较；相同则视为近义。  
- 用于盖住「主料集合因数据多/少一味而未撞上、但菜名几乎同菜」的少数情况；**主料全同已由步骤 3 挡住**的不必再依赖本步。  
- MVP 不做完整别名词表（土豆/马铃薯）；有需要再扩。

**实现要点**：

- 每成功收入一道菜：立刻记入本方案的 `usedIds`、`usedNames`、`usedMainSignatures`，并更新软用的 `usedMains`。  
- 放宽只允许关闭步骤 5；**禁止**为凑齐荤素汤数量而关闭 1～4。  
- 硬约束导致某槽位凑不齐 → 该套方案失败或减少道数的处理与现网「凑不齐 combo」一致（可少出一套 / `empty_recommend`），**不得**回退成同名双开。  
- 保留者：桶内按软惩罚排序 + 会话旋转后的**先遇到者**；后遇到的同名/同签名跳过。

**验收**：

- 同套方案内不得出现两道归一化菜名相同的菜（即使 `recipeId` 不同）。  
- 「土豆烧牛肉」与「土豆炖牛肉」不得同套（主料集合全同）。  
- 「白菜炖豆腐」与「豆腐炖白菜」不得同套（主料全同或近义名）。  
- 仅共用一道大宗配菜（如都有土豆、另一主荤不同）**允许**同套。  
- 候选不足时：可放宽「避开已用主料」，仍不得出现同名或主料签名全同。

### 3.0.8 用餐人画像软分（成员忌口 / 口味 / 小老）

**目的**：日常把「我的」每位家人的忌口、口味、年龄段用进排序（含临时访客）；非日常按本场大/小/老的**档位默认偏好**软排，并继续用**本场忌口**硬排除。  
**原则**：软分全部**不硬删**。硬排除：日常 `familyAvoids`；非日常 `partyAvoids`（规则不变）。不做忌口占比配额（后续细化）。

**当次用餐人列表**

- **日常 `daily`**  
  1. 取画像 `members[]`（`ageBand` / `taste` / `avoids`）。  
  2. 按 `scene.guestCounts` 展开访客：每档 × 该档默认偏好（菜场 §3.1.1：大=`normal`+`26_40`；小=`light`+`5_15`；老=`light`+`60_plus`；忌口空）。  
  3. 若某档有效人数低于档案：从该档成员按 `sort` 末尾省略，**不**改库。  
  4. `peopleCount` = 最终用餐人条数。  

- **聚会**（`mealType !== 'daily'`）  
  1. **仅**按 `scene.partyCounts` 展开用餐人（档位默认），**不**并入档案成员个人忌口/口味。  
  2. `peopleCount = adult+child+elder`；**`scene.combo` 须已由 `suggestPartyCombo` 算好**（确认页不编辑；见菜场 §3.2.1）。小/老**不**再改 combo，只进本软分。  
  3. 硬排除只用 `partyAvoids`；软分：有小/老 → 少辣少重口；口味按档默认。

**成员/访客忌口（软）**

- 对每道候选菜：用食材→`avoidTags` 与每位用餐人的 `avoids` 求交（见用户画像 §2.3.1）。  
- **任一人**命中 → `softPenalty += 40`（多人命中不叠乘；MVP 只加一次）。  
- 非日常展开人默认 `avoids=[]`，故本项通常为 0（除非日后给本场加人忌口）；硬排除仍靠 `partyAvoids`。

**小 / 老 → 少辣少重口**

- 若用餐人中存在 `ageBand === '5_15'`（小）或 `'60_plus'`（老）（含访客/本场档）：  
  - 菜谱口味为 `spicy` / `heavy`，或标签明示偏辣重口 → `softPenalty += 15`。  
- 无小无老：本项 0。

**口味匹配**

- 统计用餐人 `taste`；若菜谱有 `taste`（或等价标签）：  
  - 与**多数**用餐人口味一致 → 0；  
  - 冲突（例：多数 `light` 而菜 `spicy`/`heavy`）→ `softPenalty += 10`。  
- 菜谱无口味字段：本项 0（不惩罚）。

**与流水线关系**：在软排序桶内与新鲜度、reject 分一并升序；§3.0.5 旋转仍在软排之后。拼方案硬约束不变。

**验收**

- 日常：仅本人且无访客时成员忌口/口味/年龄分生效；「小」+1 访客更偏清淡且不落库。  
- 非日常：拨出 2大1小 → 有小老软分；勾选本场忌口海鲜 → 含海鲜菜硬排除；档案里孩子忌口**不**影响本场（除非用户拨了小并仅用默认、无个人忌口）。  
- 家庭/本场忌口硬排除与成员软忌口从不互相替代。

### 3.1 换一批 `swap`（随便看看）

意图：想换口味逛一逛，**不是**明确否定。

- 同 `requestId`  
- 将当前展示 plans 中菜谱 id 并入当次 `excludedDishIds`  
- `swapCount++`，feedback 记 `{ type: "swap", at }`  
- 重跑引擎  
- **不写**长期降权（下次新会话不因曾「换一批」压这些菜）  

埋点 `recommend_swap`。文案可带副标「看看别的」。

若重跑后 **plans 为空**：走 **§3.1.1**（`noNewPlans`），**不要**把推荐页换成整页空文案。

### 3.1.1 凑不出方案 / 凑不出新方案（弹窗，非空页）

| 时机 | 停留页面 | 行为 |
|------|----------|------|
| `recommend.create` 家常也凑不齐 | **输入页（确认食材）** | **不** `navigateTo` 推荐页；弹与推荐页**同一组件样式**的窄居中窗（仅标题「食材不够出菜了」+「好吧」浅底）；**不** `recommendations.add` |
| `swap` / `reject` 重跑后凑不出新方案 | **推荐页** | **保留当前展示的方案**；同上弹窗；**禁止**整页替换为仅一行空提示 |

**服务端**  
- **create**：`plans` 为空 → `{ ok:true, plans:[], emptyReason }`，**不写** `recommendations`。  
- **swap/reject**：新 `plans` 为空 → `noNewPlans: true`、`emptyReason`，**回传原 `plans` / 原 `swapCount`**；不写空 `plans`、不推进本次 `excludedDishIds` / `swapCount`。  

**埋点**：`empty_recommend`（`action=create|swap|reject`、`reasonCode?`）。

### 3.2 不行 `reject`（明确拒绝）

意图：这几道不合适。与换一批分开记。

1. 点击「不行」→ **弹出原因面板**（选项：不想吃 / 食材不对 / 太麻烦 / 最近吃过）  
2. **原因可选**：可点一项，也可点「跳过」/关闭后不带 reason 继续  
3. 无论是否选原因，都记明确拒绝：  
   - feedback `{ type: "reject", reason?, planIndex?, at }`  
   - 当前菜谱 id 并入 `excludedDishIds` 并重跑（或先关面板再换一批，交互二选一：建议拒绝后自动换一批）  
   - **长期降权**：写入 `users.rejectDownranks`（recipeId 列表）；后续会话对这些菜软降权（比 swap 强，不硬删）；有 `reason` 时可分原因微调（如 `ate_recently` 只抬新鲜度惩罚）  
4. 若重跑无新方案 → **§3.1.1**（保留当前方案 +「好吧」弹窗）  
5. 埋点 `recommend_reject`（`reason?`，`skippedReason: bool`）  

文案可带副标「这几道不太合适」。
### 3.3 去买菜 `accept`

- UI：**每个方案标题右侧**放「去买菜」（原「就他了」；表达进清单买菜，非纯确认），**不要**页底全局「可以」（否则多方案时无法标明选中哪一套）  
- 点击携带该卡 `planIndex` → 客户端**立即**跳转购买清单页 `accepted=true&planIndex=`（清单由本地已缓存方案的菜谱食材去重生成，不依赖本次云往返）  
- 同时异步调 `accept`：`accepted=true`，`acceptedAt=now`，`acceptedPlanIndex`（供「已选方案」历史）；失败可 toast「采纳未同步」，不挡清单页  
- **不写** meal_logs（已吃改由「已选方案」点选或进场确认写入）  
- 若 `scene.mealType===daily` 且搭配曾补选/修改 **且采纳的 `planKind===home`**：可选写回 `users.defaultCombo`（**不**写回 `defaultPeopleCount`；人数仅随成员增删缓存）  
- 采纳火锅 / 面条 / 水饺方案：**不**把非常规结构写回 `defaultCombo`  
- 该次会话此后可出现在 **§3.3.1 已选方案历史**（同一 `requestId` 再次改选方案则覆盖 `acceptedPlanIndex` / `acceptedAt`，列表仍只有一条会话）  
- **未来扩展**：对接买菜平台时，可在进清单之后或同入口增加「去平台加购」；接口名仍用 `accept`，埋点 `recommend_accept` 不变

### 3.3.1 已选方案历史 `listAccepted`

**入口**：「我的 → 已选方案」（与「已吃记录 / 历史」区分：后者是 `meal_logs` 列表）。

**数据**：不新建集合。查询当前 `uid` 且 `accepted === true` 的 `recommendations`，按 `acceptedAt` **倒序**。云库需索引：`uid` + `accepted` + `acceptedAt`。

**分页**：每页 **7** 条；首屏 7，列表滑到底用 **cursor**（推荐：上一页最后一条的 `acceptedAt` + `_id`）再拉 7 条。勿用无界大 `skip` 作为唯一方案（数据多了易慢）。

**每条返回（列表够用即可）**：

| 字段 | 说明 |
|------|------|
| `requestId` / `recommendationId`（文档 `_id`） | 关联点选已吃 |
| `acceptedAt` | 展示时间 |
| `scene` 摘要 | 如 mealType、人数、**x大 y小 z老**、combo（仅日常）、几顿；与推荐页 `sceneSummary` 同口径 |
| `plan` | `plans[acceptedPlanIndex]` 快照（菜名、`recipeId`、`meatVeg` 等） |
| `ateDishNames[]`（可选） | 该 `requestId` 下已有 `meal_logs` 的菜名，供勾选回显；也可客户端另调轻量接口 |

**UI**：

- 列表顶**长期小字**：如「点选标记已吃，再点取消」。  
- **首次**进入本页：悬浮气泡再说明同一句；`wx.setStorage`（或等价）记 `cookthis_plan_ate_tip_seen`，之后不再出气泡。  
- 每张卡片：时间、场景、方案内菜名；菜前**勾选样式与进场确认一致**；点选/取消行为见饮食记录 **§4.3**（即时写/删，无提交按钮）。  
- **不**提供「查看购买清单」入口；进清单仍只经推荐页「去买菜」。本页 MVP：回顾菜名 + 点选已吃。

埋点建议：`accepted_plans_list`（含 page）、`plan_ate_toggle`（`on`/`off`，`requestId`，菜名）。

### 3.4 推荐页补选搭配

- **仅日常**：若 `scene.combo` 为空，展示 `combo_fill_*`；提交可带 `persistComboToDefault`。  
- **聚会**：确认页提交前已写入 `suggestPartyCombo`；推荐页**不**展示荤素汤补选。  

### 3.4.1 有效停留 `engage`（供进场确认）

很多人不会点「去买菜」，但会在推荐页看很久。达到阈值后记入会话，供下次进场确认弹层用菜（**仍不写** `meal_logs`）。

- **阈值**：推荐页累计**可见**时长 ≥ **30 秒**  
- 计时：`onShow` 累加，`onHide` / 跳转离开暂停；换一批后针对**当前展示**的 plan 继续或重计（以当前 `planIndex` 为准）  
- 首次达到 30s：云函数 `recommend.engage` 写  
  - `engagedAt = now`（只写一次，不因后续停留改早）  
  - `dwellMs`、`engagedPlanIndex`（当时展示的那套）  
- 已有 `engagedAt`：可只更新 `dwellMs`  
- 未满 30s：**不写**，避免滑一眼也进确认列表  
- 埋点 `recommend_engage`（`dwellMs`、`planIndex`）  

进场确认如何用锚点 → 饮食记录详细设计 §3.2。确认或跳过后会话写 `entryConfirmHandled`，同锚点下次不弹。

### 3.5 非常规方案（火锅 / 面条 / 水饺）

用户**不在场景页指定**今天吃什么。引擎在家常方案之外，按画像决定要不要再给一套非常规方案。

**何时尝试**（同时满足才生成该 `planKind`，多种可尝试时只留得分最高的一套）：

| `planKind` | 画像 | 菜谱约束 | 该顿结构（相对 `scene.combo`） |
|------------|------|----------|--------------------------------|
| `hotpot` | `dishFormPrefs.hotpot === prefer` | 菜均带 `dishForms` ⊇ `hotpot` | `soup` 至少 1（锅底）；`meat`/`veg` 当荤涮/素涮凑数 |
| `noodle` | `dishFormPrefs.noodle === prefer` | 至少 1 道面（`stapleForms`/`dishForms` ⊇ `noodle`） | **仅一道面**，不再搭炒菜/素菜/汤菜（汤可写进汤面本身） |
| `dumpling` | 同上（面食一项同时覆盖水饺） | 至少 1 道饺（`stapleForms`/`dishForms` ⊇ `dumpling`） | **仅一道水饺**，不再搭炒菜；蘸料走 `seasonings` |

家常 `home` 方案**不得**把面/饺/火锅菜谱填进荤素汤 `combo`（避免「西红柿鸡蛋面 + 家常豆腐」这类误配）。

**额外加分（可叠）**：`peopleCount` 偏大或 `mealType` 为聚会（火锅）；已选食材已含典型涮品 / 面条 / 饺皮或馅；近 7 日未吃过同类**菜名**（主料重叠只降权）。

**主料例外**：锅底料、面条、饺皮等载体允许不在 `selectedIngredients` 中（仍进清单，无「未持有」标签）。涮菜、浇头、馅料仍须能从已选匹配，否则该 `planKind` 不成。

**不出**：对应 tag 为 `avoid`；近 7 日刚吃过同类**菜名**；候选菜谱或食材凑不齐。`neutral` 不主动出非常规（避免没表态却突然一桌火锅）。

**多顿**：非常规只套在 `mealSlots` 的**第一顿**；其余 slot 仍按家常拼，避免多顿都是火锅/饺子。

家庭忌口、`partyAvoids`：按涮品/锅底等**食材**的 `avoidTags` 硬排除（如 `pork`、`seafood`），不靠菜名。

## 4. 购买食材清单

### 4.1 聚合

对选中 Plan 所有 `dishes`：

- 合并 `mainIngredients`、`seasonings`（按名称去重）  
- 用食材名查 `category`（来自当次已选 / 主数据；调味无映射时归 `seasoning`，其余未知归 `other`）  

**不做**：场内已有标记、主料/调味说明标签、按「未持有优先」重排。

### 4.2 展示

- **按分类分组**（顺序示意：肉类 → 水产 → 蛋奶 → 豆制品 → 叶菜 → 根茎 → 茄果 → 豆类 → 菌菇 → 调味 → 其他）  
- 组内食材名排序后，**每行 2 个**并排勾选；奇数个时最后一行可只 1 个  
- 分类标题只用短名（如「肉类」），条目旁不写「已有 / 主料 / 调味」  

### 4.3 勾选已买

- **本地状态**即可（storage，`cookthis_shopping_checks`）  
- Key：`requestId:planIndex:swapCount`。同一推荐会话内，对某方案勾选后返回推荐页再点「去买菜」进入**同一方案**，恢复勾选。  
- **换一批 / 不行**后清空该 `requestId` 下全部勾选（方案已变）。  
- 恢复时只保留仍出现在当前清单中的食材名。  
- 埋点 `shopping_list_item_check` / `shopping_list_done`  
- 二期可云端同步 checklist  

### 4.3.1 离开清单页的导航（已定）

- **允许**返回推荐页（现有返回 / `navigateBack`），便于换方案再点「去买菜」。  
- **不**增加「回首页 / 买完了」主按钮：预计买完多数人直接退出小程序，需求已满足；回首页率不会高，不必为此做强引导。  
- **不**强制打回场景选择页。  
- 闭环靠下次打开：首页「记一下」/「今天菜场有什么」；`shopping_list_done` 可用勾选或停留等信号，不依赖点回首页。

### 4.4 底部菜谱弹层（按菜看食材）

主列表按分类买，解决摊位动线；弹层按菜回顾「这道菜要啥」，两者并存。

**入口与关闭**

- 购买食材页**底部**固定入口「看菜谱」（多顿共用同一入口，不写「本顿」），点击上推弹层。  
- **高度**：弹层整体 **不超过半屏**（`max-height: 50vh`）；标题栏固定，内容区在剩余高度内滚动。  
- **遮罩**：全屏半透明；打开时**禁止背后清单页滚动**（`catchtouchmove`）。底部「返回」可通过遮罩下的 footer 仍可见，不挡关闭逻辑。  
- **关闭**：右上角「关闭」；或点击**弹层外遮罩**（点弹层内不关闭）。  
- 关闭后回到分类勾选主界面，已买勾选状态不变。

**内容结构**

- 按当前采纳 Plan 的菜品顺序**扁平列出**（跨顿合并，**不展示**晚饭① / 午饭等顿次标识；只对照「菜 ↔ 食材」）。  
- 每一行（或每一块）：**左侧菜名**，**右侧该菜食材列表**。  
- 食材排序（单道菜内）：  
  1. **主料**在前，**调味品**在后；  
  2. 主料内部：**肉类**（`category=meat`，必要时含水产 `seafood` 紧随肉类或同属「荤」优先段）在前，**非肉主料**在后；  
  3. 同段内按名称或既定 sort 稳定排序即可。

**滚动位置**

- 弹层内容区可**上下滑动**（超出半屏高度时）。  
- **同一次停留在购买食材页内**：关闭后再打开，**恢复**上次 `scrollTop`（页内内存即可，如 Page data / 模块变量）。  
- **离开购买食材页**（`onUnload` / 返回推荐或首页等）：**重置**为顶部；下次再进清单、再开弹层从顶开始。  
- 不要求跨冷启动持久化滚动位置。

**不做**

- 弹层内勾选已买（勾选仍在分类主列表，避免同一食材按菜重复勾）。  
- 弹层替代分类主列表成为默认采购视图。

**埋点（建议）**：`shopping_recipe_sheet_open` / `shopping_recipe_sheet_close`（可带 `dwellMs`、是否滚过）。
