# 需求摘要：降低云函数调用成本

状态：需求已记录（细节待设计）  
日期：2026-10-26  
权威正文：`docs/superpowers/specs/2026-10-02-技术设计.md` §6.1；`doc/需求概述.md`「技术实现提示」

## 为什么做

当前后端以**腾讯云开发云函数**为主；用户量起来后，按次调用 + 时长会推高账单。需在不迁栈的前提下，用产品/工程手段压调用量。

## 目标

- 减少**用户路径**上的云函数调用次数（尤其高频：登录校验、画像读、食材列表、埋点、推荐读写）。
- 在可接受范围内降低单次执行时长与回包体积。
- **不**削弱：鉴权、写库一致性、忌口/推荐等安全与正确性。

## 候选手段（设计时再定优先级与验收指标）

| 方向 | 例子 |
|------|------|
| 端上 TTL 缓存 | `auth`/`profile`/`ingredients` 结果本地缓存；过期或主动失效再拉 |
| 请求合并 | 一屏多读合成一次；`analytics` 批量 flush |
| 静态下发 | 别名、城货架、节日包随小程序包或存储 CDN，避免每次函数读库 |
| 函数内缓存 | 实例级食材/菜谱元数据缓存（已有方向，可扩展） |
| 读路径评估 | 只读场景是否可用云数据库客户端直读（规则收紧）vs 继续函数 |

## 非目标

- 现阶段不迁自建服务器 / 换云
- 不为省钱关掉必要鉴权或把敏感写逻辑放到端上

## 验收（上线专项时再量化）

- 典型路径（进确认 → create → 去买菜）云函数调用次数对比基线下降（目标比例设计时定）
- 主路径功能与安全回归通过
